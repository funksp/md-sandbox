# Payment Integrity Hypothesis Pipeline: Implementation Spec

**Audience:** the implementing agent.
**Purpose:** replace "cluster the signals, then explain each cluster" with "strip out benign growth, find what changed in the billing, and pivot to patterns that recur across unrelated providers."
**Status of this document:** design is complete. Every SQL block with a `-- BLOCK:` header was executed end to end on synthetic claims (see Appendix C). Nothing here has been run on real tables, so column names, data quirks, and thresholds must be confirmed in Stage 0.

---

## 0. Read this first

### 0.1 What you are building

The upstream "emerging spend" pipeline flags provider series (`PROV_BIL_TIN × LOB_CAT × HCC_FIX × SERVICE_CATEGORY`) whose total allowed dollars stepped up more than peers. Most of those step-ups are benign: more patients, a new fee schedule, an acquisition. You are building the layer that sits downstream and turns those signals into **payment integrity concepts**: a billing mechanism, written as a rule, sized in dollars, that recurs across many unrelated providers.

### 0.2 Pipeline at a glance

```
Stage 0  Setup checks            confirm tables, columns, data quirks        (SQL + short report)
Stage 1  Base tables             signals, controls, windows, netted lines    (SQL)
Stage 2  Decomposition           split each step-up into 7 components        (SQL)
Stage 3  Benign gates            close artifacts / volume / price in SQL     (SQL)
Stage 4  Pattern mining          what billing patterns grew, net of peers    (SQL)
Stage 5  Pivot                   pattern -> list of TINs; keep recurring     (SQL + small Python)
Stage 6  Hypothesis loop         state mechanism, test, red-team, size       (agents)
Stage 7  Evaluation              waterfall, control test, backtest, metrics  (SQL + report)
```

Stages 0–5 and 7 are deterministic code. Agents reason only in Stage 6. Do not use an LLM to do anything a query can do.

### 0.3 Ground rules

1. **Do Stage 0 before anything else.** Several later steps have a fallback that depends on what Stage 0 finds.
2. **Do not tune thresholds during the first full run.** All thresholds live in `PIH_CONFIG` (Section 2.3) or are stated in the gate catalog. They are reasoned defaults, not empirically fitted. On the first run, record how many records each threshold drops; propose changes only afterwards, with those counts.
3. **Never drop a record silently.** Every subject ends with a disposition and a reason, the same way upstream writes `review_exclusion_reason`.
4. **Controls go through everything signals go through.** The control sample (Section 4.4) exists to test whether the upstream signals add anything. It is useless if it is processed differently.
5. **Sensitive identifiers.** `MBR_ID` and claim IDs never appear in ledgers, dossiers, or chat. `PROV_BIL_TIN` can be an individual's SSN, so mask it (hash or surrogate key) in anything a human reads outside the secure environment. Suppress any reported count of members below your organization's minimum cell size.
6. **Do not invent policy citations.** In Stage 6 you may say "this looks like an add-on code billed without its primary." You may not cite a specific policy, edit, or contract term unless a human supplied it.
7. **Dry run first.** Run Stages 1–5 on one variant and about 50 signals before the full run. Check the acceptance criteria at the end of each stage.

### 0.4 Checkpoints: stop and report to the human

| After | Report |
|---|---|
| Stage 0 | The filled-in checklist from Section 3, and any check that failed |
| Stage 3 | The waterfall (Section 6.6) and gate disposition counts, for signals and controls side by side |
| Stage 5 | The ranked list of recurring patterns with tags, and the enrichment result |
| Stage 6 | The hypothesis ledger and dossiers for survivors |

## 1. Definitions

| Term | Meaning |
|---|---|
| **Concept** | A billing mechanism (not a provider) that likely causes overpayment, expressible as a rule, sized in dollars, recurring across unrelated providers |
| **Signal** | One row of upstream output: a TIN × cell flagged as an emerging-spend anomaly in one variant |
| **Cell** | `LOB_CAT × HCC_FIX × SERVICE_CATEGORY` |
| **Variant** | `NONPAR`, `PAR`, or `BH`: the three upstream model populations |
| **Subject** | A signal or a matched control. Everything downstream is keyed by `SUBJECT_ID` |
| **Window** | A pre period and a post period of equal length `K` months. Post starts at the upstream `change_point_month` and ends at the last data month |
| **Peer** | Another TIN in the same upstream `PEER_GROUP_KEY`, always excluding the subject's own TIN |
| **Netted line** | One service: member × TIN × date × code × modifier set × site, after summing adjustments and reversals |
| **Item** | `CODE|MODSET|SITE`: the unit at which price is compared like for like |
| **Pattern** | A token built from a netted line or event (Section 7.1), such as a code plus modifier, or a pair of codes in one event |
| **Intensity** | The part of a step-up not explained by patient volume or price: events per patient-month, lines per event, units per line, and service mix |
| **TIN group** | A set of TINs that appear to be related (shared members or clinicians). "Recurring" means recurring across TIN groups, not TINs |

### 2.1 Source views you must create

Create three views so that every later block can run unchanged. Map real column names to the names below.

**`SRC_SIGNALS`**: union of the three upstream output tables (`IRG_MONITORING_EMERGING_*_ANOMALIES`).

The claims bridge table may only contain lines for signal series. This pipeline needs peer lines too, so build from the source tables, not the bridge.

### 2.3 Configuration

```sql
-- BLOCK: B00_CONFIG
CREATE OR REPLACE TABLE PIH_CONFIG AS
SELECT
  CAST('2026-03-01' AS DATE) AS DATA_END_MONTH,          -- last complete service month in the source tables
  50000.0 AS MIN_INTENSITY_USD,          -- annualized peer-adjusted intensity needed to pass on dollars alone
  10000.0 AS MIN_PATTERN_EXCESS_USD,     -- annualized excess for one pattern at one subject to count
  10      AS MIN_PATTERN_LINES,          -- post-period lines carrying the pattern
  5       AS MIN_PATTERN_MEMBERS,        -- post-period members carrying the pattern
  10      AS MIN_PEERS,                  -- qualified peer TINs needed to peer-adjust the decomposition
  10      AS PEER_MIN_MEMBERS,           -- a peer TIN needs this many members in each period to qualify
  5000.0  AS PEER_MIN_ALLOWED,           -- and this much allowed in each period
  5       AS PATTERN_PEER_MIN_TINS,      -- peer TINs billing a pattern pre-period, to trust its peer growth rate
  5000.0  AS PATTERN_PEER_MIN_ALLOWED,   -- peer pre-period dollars on a pattern, same purpose
  5       AS MIN_INDEP_GROUPS,           -- independent TIN groups for a pattern to be "recurring"
  0.60    AS MAX_TOP_GROUP_SHARE;        -- no single TIN group may hold more than this share of a pattern's excess
```

`MIN_INTENSITY_USD` is lower than upstream's $75K because intensity is only one slice of the total excess.

## 3. Stage 0: Setup checks

Run each check, record the result, apply the fallback if it fails. Report all of them at the first checkpoint.

| # | Check | Pass criterion | If it fails |
|---|---|---|---|
| 0.1 | Locate the three source claim tables, three signal tables, three peered staging tables | All found | See 2.1 for rebuilding peer groups. Missing claim tables: stop |
| 0.2 | Which signal set do you have: top 1000, all Gate-3 passers, or all Stage-3-significant? | Recorded | Proceed with what you have; note it |
| 0.3 | `CHANGE_POINT_MONTH` convention: is it the first month of the post segment? Check against upstream `months_since_change` (it should equal months from change point through `DATA_END_MONTH`, inclusive or exclusive) | Confirmed first post month | If it is the last pre month, add one month when building `PIH_SIGNALS` |
| 0.4 | Reconciliation: for 200 random signals, monthly `SUM(AMT_ALLOWED)` from `SRC_CLAIM_LINES` (with the variant's par filter) equals upstream monthly `ALLOWED_AMT` | Within 1% for at least 95% of series | Stop. The line-level source does not match what the signals were computed on; find out why before continuing |
| 0.5 | Adjustments: share of rows with `AMT_ALLOWED < 0`; whether a reversal shares `CLM_ID_LONG` with its original | Recorded | No action needed: the netting in B03 does not depend on claim ID |
| 0.6 | `UNITS`: share NULL or ≤ 0 on rows with `AMT_ALLOWED > 0`, by `CLM_TYPE` | Under 10% | Units are set to 1 where missing. If over 10% in a cell, treat that cell's UNITS and PRICE components as one combined "rate" component and say so |

## 4. Stage 1: Base tables

### 4.1 Signals and scope

```sql
-- BLOCK: B01_SIGNALS
CREATE OR REPLACE TABLE PIH_SIGNALS AS
SELECT
  VARIANT || '|' || PROV_BIL_TIN || '|' || LOB_CAT || '|' || HCC_FIX || '|' || SERVICE_CATEGORY AS SIGNAL_ID,
  VARIANT, PROV_BIL_TIN, LOB_CAT, HCC_FIX, SERVICE_CATEGORY,
  PEER_GROUP_KEY, PEER_GROUP_LEVEL, METHOD_FAMILY, PRIMARY_DRIVER,
  CAST(CHANGE_POINT_MONTH AS DATE) AS CHANGE_POINT_MONTH,
  UPSTREAM_EXCESS
FROM SRC_SIGNALS;
```

Scope is every TIN in any peer group that contains a signal. These are the TINs whose lines you need.

```sql
-- BLOCK: B02_SCOPE
CREATE OR REPLACE TABLE PIH_SCOPE AS
SELECT DISTINCT pm.VARIANT, pm.PEER_GROUP_KEY, pm.PROV_BIL_TIN, pm.LOB_CAT, pm.HCC_FIX, pm.SERVICE_CATEGORY
FROM SRC_PEER_MAP pm
JOIN (SELECT DISTINCT VARIANT, PEER_GROUP_KEY FROM PIH_SIGNALS) g
  ON g.VARIANT = pm.VARIANT AND g.PEER_GROUP_KEY = pm.PEER_GROUP_KEY;
```

### 4.2 Netted lines

One row per member × TIN × date × code × modifier set × site. Summing within that key nets reversals and adjustments without relying on claim ID conventions. Rows that net to zero or below are dropped. Genuine duplicate billing survives as `N_CLAIM_IDS > 1` and inflated units.

```sql
-- BLOCK: B03_LINES
CREATE OR REPLACE TABLE PIH_LINES AS
WITH scope_cells AS (
  SELECT DISTINCT PROV_BIL_TIN, LOB_CAT, HCC_FIX, SERVICE_CATEGORY FROM PIH_SCOPE
),
raw AS (
  SELECT
    cl.MBR_ID, cl.PROV_BIL_TIN, cl.LOB_CAT, cl.HCC_FIX, cl.SERVICE_CATEGORY,
    cl.PROV_SVC_PAR_STAT, cl.CLM_TYPE, cl.FDOS_LN,
    CAST(DATE_TRUNC('MONTH', cl.FDOS_LN) AS DATE) AS SVC_MONTH,
    COALESCE(CAST(cl.EVENT_KEY AS VARCHAR),
             CAST(cl.MBR_ID AS VARCHAR) || '|' || cl.PROV_BIL_TIN || '|' || CAST(cl.FDOS_LN AS VARCHAR)) AS EVENT_ID,
    COALESCE(NULLIF(TRIM(cl.CPT_PROC_CD), ''),
             'REV' || COALESCE(NULLIF(TRIM(cl.REV_CD), ''), 'NA')) AS CODE,
    COALESCE(NULLIF(ARRAY_TO_STRING(ARRAY_SORT(ARRAY_DISTINCT(ARRAY_CONSTRUCT_COMPACT(
               NULLIF(TRIM(cl.MOD1), ''), NULLIF(TRIM(cl.MOD2), ''),
               NULLIF(TRIM(cl.MOD3), ''), NULLIF(TRIM(cl.MOD4), '')))), '-'), ''), 'NONE') AS MODSET,
    COALESCE(NULLIF(TRIM(cl.POS), ''), 'BT' || LEFT(cl.BILL_TYPE, 3), 'NA') AS SITE,
    cl.DX1, cl.PLATFORM, cl.AHRQ_PROC_DTL_CATGY_DESC, cl.BILLED_PROC_CD, cl.CLM_ID_LONG,
    cl.AMT_ALLOWED, cl.AMT_PD, cl.AMT_BIL, cl.UNITS
  FROM SRC_CLAIM_LINES cl
  JOIN scope_cells sc
    ON sc.PROV_BIL_TIN = cl.PROV_BIL_TIN AND sc.LOB_CAT = cl.LOB_CAT
   AND sc.HCC_FIX = cl.HCC_FIX AND sc.SERVICE_CATEGORY = cl.SERVICE_CATEGORY
)
SELECT
  MBR_ID, PROV_BIL_TIN, LOB_CAT, HCC_FIX, SERVICE_CATEGORY, PROV_SVC_PAR_STAT, CLM_TYPE,
  FDOS_LN, SVC_MONTH, EVENT_ID, CODE, MODSET, SITE,
  CODE || '|' || MODSET || '|' || SITE AS ITEM,
  MIN(DX1) AS DX1,
  LEFT(MIN(DX1), 3) AS DX3,
  MIN(PLATFORM) AS PLATFORM,
  MIN(AHRQ_PROC_DTL_CATGY_DESC) AS AHRQ_CAT,
  MIN(BILLED_PROC_CD) AS BILLED_CODE,
  COUNT(*) AS N_RAW_ROWS,
  COUNT(DISTINCT CLM_ID_LONG) AS N_CLAIM_IDS,
  SUM(AMT_ALLOWED) AS ALLOWED,
  SUM(AMT_PD) AS PAID,
  SUM(AMT_BIL) AS BILLED,
  CASE WHEN SUM(UNITS) IS NULL OR SUM(UNITS) <= 0 THEN 1 ELSE SUM(UNITS) END AS UNITS_ADJ
FROM raw
GROUP BY MBR_ID, PROV_BIL_TIN, LOB_CAT, HCC_FIX, SERVICE_CATEGORY, PROV_SVC_PAR_STAT, CLM_TYPE,
         FDOS_LN, SVC_MONTH, EVENT_ID, CODE, MODSET, SITE
HAVING SUM(AMT_ALLOWED) > 0;
```

If `RENDERING_NPI` exists, add `MIN(RENDERING_NPI) AS RENDERING_NPI` to the select.

Attach variant and peer group. The par-status filter reproduces the upstream population definitions; the BH variant takes any par status because its scope is already limited to BH cells.

```sql
-- BLOCK: B04_LINES_S
CREATE OR REPLACE TABLE PIH_LINES_S AS
SELECT sc.VARIANT, sc.PEER_GROUP_KEY, l.*
FROM PIH_LINES l
JOIN PIH_SCOPE sc
  ON sc.PROV_BIL_TIN = l.PROV_BIL_TIN AND sc.LOB_CAT = l.LOB_CAT
 AND sc.HCC_FIX = l.HCC_FIX AND sc.SERVICE_CATEGORY = l.SERVICE_CATEGORY
WHERE (sc.VARIANT = 'NONPAR' AND l.PROV_SVC_PAR_STAT = 'N' AND l.HCC_FIX <> 'IP')
   OR (sc.VARIANT = 'PAR'    AND l.PROV_SVC_PAR_STAT = 'P')
   OR (sc.VARIANT = 'BH');
```

### 4.3 Why netted lines and not raw rows

- Adjustments would otherwise look like extra lines and extra dollars in whichever month they posted.
- "Lines per event" becomes "distinct services per event," which is the quantity that unbundling changes.
- It gives one consistent definition of a line for price comparison.

### 4.4 Subjects: signals plus matched controls

Each signal gets one control: a series from the same variant and peer group whose TIN has no signal anywhere, closest in recent size. The control inherits the signal's change-point month, so it is analyzed over the same window. Controls answer one question: do the patterns you find show up just as often in series that upstream did not flag?

```sql
-- BLOCK: B05_SUBJECTS
CREATE OR REPLACE TABLE PIH_SUBJECTS AS
WITH recent AS (
  SELECT l.VARIANT, l.PEER_GROUP_KEY, l.PROV_BIL_TIN, SUM(l.ALLOWED) AS RECENT_ALLOWED
  FROM PIH_LINES_S l
  CROSS JOIN PIH_CONFIG c
  WHERE l.SVC_MONTH > DATEADD('MONTH', -3, c.DATA_END_MONTH)
  GROUP BY 1, 2, 3
),
cand AS (
  SELECT
    sg.SIGNAL_ID, sg.METHOD_FAMILY, sg.PRIMARY_DRIVER, sg.CHANGE_POINT_MONTH, sg.PEER_GROUP_LEVEL,
    sc.VARIANT, sc.PEER_GROUP_KEY, sc.PROV_BIL_TIN, sc.LOB_CAT, sc.HCC_FIX, sc.SERVICE_CATEGORY,
    ABS(LN(rc.RECENT_ALLOWED) - LN(rs.RECENT_ALLOWED)) AS SIZE_DIST
  FROM PIH_SIGNALS sg
  JOIN recent rs
    ON rs.VARIANT = sg.VARIANT AND rs.PEER_GROUP_KEY = sg.PEER_GROUP_KEY AND rs.PROV_BIL_TIN = sg.PROV_BIL_TIN
  JOIN PIH_SCOPE sc
    ON sc.VARIANT = sg.VARIANT AND sc.PEER_GROUP_KEY = sg.PEER_GROUP_KEY
  JOIN recent rc
    ON rc.VARIANT = sc.VARIANT AND rc.PEER_GROUP_KEY = sc.PEER_GROUP_KEY AND rc.PROV_BIL_TIN = sc.PROV_BIL_TIN
  WHERE sc.PROV_BIL_TIN NOT IN (SELECT PROV_BIL_TIN FROM PIH_SIGNALS)
    AND rs.RECENT_ALLOWED > 0 AND rc.RECENT_ALLOWED > 0
  QUALIFY ROW_NUMBER() OVER (PARTITION BY sg.SIGNAL_ID ORDER BY SIZE_DIST, sc.PROV_BIL_TIN) = 1
)
SELECT SIGNAL_ID AS SUBJECT_ID, 'SIGNAL' AS ROLE, CAST(NULL AS VARCHAR) AS MATCHED_SIGNAL_ID,
       VARIANT, PROV_BIL_TIN, LOB_CAT, HCC_FIX, SERVICE_CATEGORY, PEER_GROUP_KEY, PEER_GROUP_LEVEL,
       METHOD_FAMILY, PRIMARY_DRIVER, CHANGE_POINT_MONTH, UPSTREAM_EXCESS
FROM PIH_SIGNALS
UNION ALL
SELECT 'CTL|' || SIGNAL_ID, 'CONTROL', SIGNAL_ID,
       VARIANT, PROV_BIL_TIN, LOB_CAT, HCC_FIX, SERVICE_CATEGORY, PEER_GROUP_KEY, PEER_GROUP_LEVEL,
       METHOD_FAMILY, PRIMARY_DRIVER, CHANGE_POINT_MONTH, CAST(NULL AS DOUBLE)
FROM cand;
```

The same control TIN can be matched to more than one signal. That is acceptable; count distinct TINs where it matters. If you were given the full Stage-3-significant set as `SRC_SIGNALS`, controls are drawn from series that were not significant, which is the cleaner comparison.

### 4.5 Windows

Three window types:

| Type | Pre | Post | Used for |
|---|---|---|---|
| `ADJ` (primary) | The `K` months immediately before the change point | Change point through `DATA_END_MONTH` (`K` months) | Standard-history subjects |
| `YOY` (sensitivity) | The same calendar months one year earlier | Same as `ADJ` | Standard-history subjects, to check that seasonality is not driving the result |
| `LVL` | None | Last 3 data months | Limited-history subjects, which have no usable pre period |

Equal-length pre and post periods matter: distinct member counts are only comparable across periods of the same length.

```sql
-- BLOCK: B06_WINDOWS
CREATE OR REPLACE TABLE PIH_WINDOWS AS
WITH k AS (
  SELECT DISTINCT s.CHANGE_POINT_MONTH AS POST_START, c.DATA_END_MONTH AS POST_END,
         DATEDIFF('MONTH', s.CHANGE_POINT_MONTH, c.DATA_END_MONTH) + 1 AS K
  FROM PIH_SUBJECTS s
  CROSS JOIN PIH_CONFIG c
  WHERE s.METHOD_FAMILY = 'STANDARD_HISTORY' AND s.CHANGE_POINT_MONTH IS NOT NULL
)
SELECT 'ADJ|' || CAST(POST_START AS VARCHAR) AS WINDOW_ID, 'ADJ' AS WINDOW_TYPE, POST_START, POST_END, K,
       DATEADD('MONTH', -K, POST_START) AS PRE_START, DATEADD('MONTH', -1, POST_START) AS PRE_END
FROM k
UNION ALL
SELECT 'YOY|' || CAST(POST_START AS VARCHAR), 'YOY', POST_START, POST_END, K,
       DATEADD('MONTH', -12, POST_START), DATEADD('MONTH', -12, POST_END)
FROM k
WHERE K <= 12
UNION ALL
SELECT 'LVL', 'LVL', DATEADD('MONTH', -2, c.DATA_END_MONTH), c.DATA_END_MONTH, 3,
       CAST(NULL AS DATE), CAST(NULL AS DATE)
FROM PIH_CONFIG c;
```

```sql
-- BLOCK: B07_SUBJECT_WINDOW
CREATE OR REPLACE TABLE PIH_SUBJECT_WINDOW AS
SELECT s.SUBJECT_ID, w.WINDOW_ID, w.WINDOW_TYPE,
       CASE WHEN w.WINDOW_TYPE IN ('ADJ', 'LVL') THEN 1 ELSE 0 END AS IS_PRIMARY
FROM PIH_SUBJECTS s
JOIN PIH_WINDOWS w
  ON (s.METHOD_FAMILY = 'STANDARD_HISTORY' AND w.WINDOW_TYPE IN ('ADJ', 'YOY')
      AND w.POST_START = s.CHANGE_POINT_MONTH)
  OR (s.METHOD_FAMILY = 'LIMITED_HISTORY' AND w.WINDOW_TYPE = 'LVL');

CREATE OR REPLACE TABLE PIH_SCOPE_WINDOW AS
SELECT DISTINCT s.VARIANT, s.PEER_GROUP_KEY, sw.WINDOW_ID
FROM PIH_SUBJECTS s
JOIN PIH_SUBJECT_WINDOW sw ON sw.SUBJECT_ID = s.SUBJECT_ID;
```

### 4.6 Lines by window, and TIN-by-window aggregates

Each peer group only needs the windows used by its own subjects.

```sql
-- BLOCK: B08_TW_LINES
CREATE OR REPLACE TABLE PIH_TW_LINES AS
SELECT
  sw.WINDOW_ID,
  CASE WHEN l.SVC_MONTH BETWEEN w.POST_START AND w.POST_END THEN 'POST' ELSE 'PRE' END AS PERIOD,
  l.*
FROM PIH_LINES_S l
JOIN PIH_SCOPE_WINDOW sw ON sw.VARIANT = l.VARIANT AND sw.PEER_GROUP_KEY = l.PEER_GROUP_KEY
JOIN PIH_WINDOWS w ON w.WINDOW_ID = sw.WINDOW_ID
WHERE l.SVC_MONTH BETWEEN w.POST_START AND w.POST_END
   OR (w.PRE_START IS NOT NULL AND l.SVC_MONTH BETWEEN w.PRE_START AND w.PRE_END);
```

```sql
-- BLOCK: B09_TW
CREATE OR REPLACE TABLE PIH_TW AS
SELECT
  VARIANT, PEER_GROUP_KEY, PROV_BIL_TIN, WINDOW_ID, PERIOD,
  SUM(ALLOWED) AS A,
  SUM(PAID) AS PD,
  SUM(BILLED) AS BL,
  COUNT(DISTINCT MBR_ID) AS D,                                                             -- distinct members
  COUNT(DISTINCT CAST(MBR_ID AS VARCHAR) || '|' || CAST(SVC_MONTH AS VARCHAR)) AS MM,      -- active member-months
  COUNT(DISTINCT EVENT_ID) AS E,                                                           -- events
  COUNT(*) AS L,                                                                           -- netted lines
  SUM(UNITS_ADJ) AS U                                                                      -- units
FROM PIH_TW_LINES
GROUP BY 1, 2, 3, 4, 5;

CREATE OR REPLACE TABLE PIH_TW_ITEM AS
SELECT
```

## 5. Stage 2: Decomposition

### 5.1 The idea

Monthly allowed dollars can be written as a product:

```
allowed per month = members
                  × active months per member
                  × events per active member-month
                  × lines per event
                  × allowed per line
```

and allowed per line splits further into service mix, units per line, and price. That gives seven components:

| Component | Formula | What a rise means | Class |
|---|---|---|---|
| `PANEL` | distinct members `D` | More patients | Volume |
| `FREQ` | `MM / D` | Patients active in more months of the window | Volume (see note) |
| `EVENTS` | `E / MM` | More visits per patient per month | Intensity |
| `LINES` | `L / E` | More services per visit | Intensity |
| `MIX` | shift in share of lines across items | Costlier items: higher code levels, new codes, modifiers, site changes | Intensity |
| `UNITS` | units per line within the same item | More units billed on the same service | Intensity |
| `PRICE` | allowed per unit within the same item | Fee schedule, contract, or charge change | Price |

**Intensity dollars** are the sum of `EVENTS`, `LINES`, `MIX`, and `UNITS`, after subtracting what peers did. This number replaces upstream's total excess as the ranking dollar.

Three things to know when reading the components:

- **`PANEL` and `FREQ` move together.** When a provider gains patients partway through a window, those patients are active in fewer months, so `FREQ` dips mechanically while `PANEL` rises. Their sum is the change in active member-months, which is the honest measure of volume. That is why `FREQ` is classed as volume. Real frequency escalation (the same patients brought back more often) is caught separately by gate V7, which measures it on continuing patients only, and by the `M1` tokens in Stage 4.
- **`LINES` and `MIX` move together.** Adding a cheap service to every visit raises lines per event and lowers the average allowed per line at the same time. Read them as a pair; their sum is what the added billing is worth.
- **Interactions are shared out.** If a provider gains patients and also bills more per patient, the extra billing on the new patients is split between volume and intensity. Intensity dollars are therefore a conservative figure.

### 5.2 The math

Let subscript 0 be the pre period and 1 the post period, and `K` the months in each.

**Step 1: log contributions.** For the four ratio components the log contribution is the log change:

```
g_PANEL  = ln(D1 / D0)
g_FREQ   = ln((MM1/D1) / (MM0/D0))
g_EVENTS = ln((E1/MM1) / (E0/MM0))
g_LINES  = ln((L1/E1) / (L0/E0))
```

**Step 2: split allowed per line.** Let `a = A / L` (allowed per line). For each item `k`: `w_k` is its share of lines, `u_k` its units per line, `p_k` its allowed per unit, so `a = Σ w_k · u_k · p_k`. With bars meaning the average of the pre and post values:

```
mix_term   = Σ_k  avg(u_k·p_k) · (w_k1 − w_k0)
units_term = Σ_k  avg(w_k) · avg(p_k) · (u_k1 − u_k0)
price_term = Σ_k  avg(w_k) · avg(u_k) · (p_k1 − p_k0)
```

These three sum exactly to `a1 − a0`. If an item exists in only one period, use that period's `u_k` and `p_k` for both, so its whole effect lands in mix.

**Step 3: convert to log contributions.** With `Lmean(x, y) = (x − y) / (ln x − ln y)` (the logarithmic mean; equal to `x` when `x = y`):

```
g_MIX = mix_term / Lmean(a1, a0)     g_UNITS = units_term / Lmean(a1, a0)     g_PRICE = price_term / Lmean(a1, a0)
```

The seven `g` values sum exactly to `ln(A1 / A0)`.

**Step 4: peer-adjust.** For each component, take the **median** of `g` across qualified peer TINs (same variant, peer group, and window; excluding the subject's TIN; each with at least `PEER_MIN_MEMBERS` members and `PEER_MIN_ALLOWED` dollars in both periods). Call it `pg`. If fewer than `MIN_PEERS` peers qualify, set every `pg` to 0 and mark `PEER_ADJ_OK = 0`.

**Step 5: dollars.**

```
ADJ_component = 12 × Lmean(A1/K, A0/K) × (g − pg)
PEER_TREND    = 12 × Lmean(A1/K, A0/K) × Σ pg
```

The seven adjusted components plus `PEER_TREND` sum exactly to the annualized raw change `12 × (A1 − A0) / K`. This identity is your main correctness check.

Why medians of per-TIN changes and not pooled peer totals: pooled totals are dominated by the largest TINs in the group.

```sql
-- BLOCK: B10_DECOMP_G
CREATE OR REPLACE TABLE PIH_DECOMP_G AS
WITH w AS (
  SELECT
    t.VARIANT, t.PEER_GROUP_KEY, t.PROV_BIL_TIN, t.WINDOW_ID, MAX(win.K) AS K,

    SUM(CASE WHEN t.PERIOD = 'POST' THEN t.MM ELSE 0 END) AS MM1,
    SUM(CASE WHEN t.PERIOD = 'PRE'  THEN t.E  ELSE 0 END) AS E0,

    SUM(CASE WHEN t.PERIOD = 'POST' THEN t.L  ELSE 0 END) AS L1,

    SUM(CASE WHEN t.PERIOD = 'POST' THEN t.U  ELSE 0 END) AS U1,

    SUM(CASE WHEN t.PERIOD = 'POST' THEN t.PD ELSE 0 END) AS PD1,
    SUM(CASE WHEN t.PERIOD = 'PRE'  THEN t.BL ELSE 0 END) AS BL0,
    SUM(CASE WHEN t.PERIOD = 'POST' THEN t.BL ELSE 0 END) AS BL1
  FROM PIH_TW t
  JOIN PIH_WINDOWS win ON win.WINDOW_ID = t.WINDOW_ID
  WHERE win.WINDOW_TYPE <> 'LVL'
  GROUP BY 1, 2, 3, 4
),
item AS (
  SELECT
    VARIANT, PEER_GROUP_KEY, PROV_BIL_TIN, WINDOW_ID, ITEM,
    SUM(CASE WHEN PERIOD = 'PRE'  THEN L_K ELSE 0 END) AS L0K,
    SUM(CASE WHEN PERIOD = 'POST' THEN L_K ELSE 0 END) AS L1K,
    SUM(CASE WHEN PERIOD = 'PRE'  THEN U_K ELSE 0 END) AS U0K,
    SUM(CASE WHEN PERIOD = 'POST' THEN U_K ELSE 0 END) AS U1K,
    SUM(CASE WHEN PERIOD = 'PRE'  THEN A_K ELSE 0 END) AS A0K,
    SUM(CASE WHEN PERIOD = 'POST' THEN A_K ELSE 0 END) AS A1K
  FROM PIH_TW_ITEM
  GROUP BY 1, 2, 3, 4, 5
),
item2 AS (
  SELECT
    i.VARIANT, i.PEER_GROUP_KEY, i.PROV_BIL_TIN, i.WINDOW_ID, i.ITEM,
    i.L0K * 1.0 / w.L0 AS W0,
    i.L1K * 1.0 / w.L1 AS W1,
    COALESCE(i.U0K * 1.0 / NULLIF(i.L0K, 0), i.U1K * 1.0 / NULLIF(i.L1K, 0)) AS UL0,
    COALESCE(i.U1K * 1.0 / NULLIF(i.L1K, 0), i.U0K * 1.0 / NULLIF(i.L0K, 0)) AS UL1,
    COALESCE(i.A0K / NULLIF(i.U0K, 0), i.A1K / NULLIF(i.U1K, 0)) AS P0,
    COALESCE(i.A1K / NULLIF(i.U1K, 0), i.A0K / NULLIF(i.U0K, 0)) AS P1
  FROM item i
  JOIN w
    ON w.VARIANT = i.VARIANT AND w.PEER_GROUP_KEY = i.PEER_GROUP_KEY
   AND w.PROV_BIL_TIN = i.PROV_BIL_TIN AND w.WINDOW_ID = i.WINDOW_ID
  WHERE w.L0 > 0 AND w.L1 > 0
),
bennet AS (
  SELECT
    VARIANT, PEER_GROUP_KEY, PROV_BIL_TIN, WINDOW_ID,
    SUM(((UL0 * P0 + UL1 * P1) / 2) * (W1 - W0))            AS MIX_TERM,
    SUM(((W0 + W1) / 2) * ((P0 + P1) / 2) * (UL1 - UL0))    AS UNITS_TERM,
    SUM(((W0 + W1) / 2) * ((UL0 + UL1) / 2) * (P1 - P0))    AS PRICE_TERM
  FROM item2
  GROUP BY 1, 2, 3, 4
),
base AS (
  SELECT
    w.*, b.MIX_TERM, b.UNITS_TERM, b.PRICE_TERM,
    w.A0 / NULLIF(w.L0, 0) AS APL0,
    w.A1 / NULLIF(w.L1, 0) AS APL1,
    CASE WHEN w.A0 > 0 AND w.A1 > 0 THEN 1 ELSE 0 END AS DECOMPOSABLE
  FROM w
  LEFT JOIN bennet b
    ON b.VARIANT = w.VARIANT AND b.PEER_GROUP_KEY = w.PEER_GROUP_KEY
   AND b.PROV_BIL_TIN = w.PROV_BIL_TIN AND b.WINDOW_ID = w.WINDOW_ID
),
lm AS (
  SELECT
    base.*,
    CASE WHEN DECOMPOSABLE = 1 THEN
      (CASE WHEN ABS(A1 - A0) < 1e-9 * A0 THEN A0
            ELSE (A1 - A0) / (LN(NULLIF(A1, 0)) - LN(NULLIF(A0, 0))) END) / K
    END AS LM_AM,                      -- log mean of MONTHLY allowed
    CASE WHEN DECOMPOSABLE = 1 THEN
      (CASE WHEN ABS(APL1 - APL0) < 1e-9 * APL0 THEN APL0
            ELSE (APL1 - APL0) / (LN(NULLIF(APL1, 0)) - LN(NULLIF(APL0, 0))) END)
    END AS LM_APL                      -- log mean of allowed per line
  FROM base
)
SELECT
  lm.*,
  CASE WHEN DECOMPOSABLE = 1 THEN LN(NULLIF(D1, 0) * 1.0 / NULLIF(D0, 0)) END AS G_PANEL,
  CASE WHEN DECOMPOSABLE = 1 THEN LN((MM1 * 1.0 / NULLIF(D1, 0)) / NULLIF(MM0 * 1.0 / NULLIF(D0, 0), 0)) END AS G_FREQ,
  CASE WHEN DECOMPOSABLE = 1 THEN LN((E1 * 1.0 / NULLIF(MM1, 0)) / NULLIF(E0 * 1.0 / NULLIF(MM0, 0), 0)) END AS G_EVENTS,
  CASE WHEN DECOMPOSABLE = 1 THEN LN((L1 * 1.0 / NULLIF(E1, 0)) / NULLIF(L0 * 1.0 / NULLIF(E0, 0), 0)) END AS G_LINES,
  CASE WHEN DECOMPOSABLE = 1 THEN MIX_TERM   / NULLIF(LM_APL, 0) END AS G_MIX,
  CASE WHEN DECOMPOSABLE = 1 THEN UNITS_TERM / NULLIF(LM_APL, 0) END AS G_UNITS,
  CASE WHEN DECOMPOSABLE = 1 THEN PRICE_TERM / NULLIF(LM_APL, 0) END AS G_PRICE,
  CASE WHEN DECOMPOSABLE = 1
        AND D0 >= c.PEER_MIN_MEMBERS AND D1 >= c.PEER_MIN_MEMBERS
        AND A0 >= c.PEER_MIN_ALLOWED AND A1 >= c.PEER_MIN_ALLOWED THEN 1 ELSE 0 END AS QUALIFIED_PEER
FROM lm
CROSS JOIN PIH_CONFIG c;
```

```sql
-- BLOCK: B11_DECOMP
CREATE OR REPLACE TABLE PIH_DECOMP AS
WITH subj AS (

  FROM PIH_SUBJECTS s
  JOIN PIH_SUBJECT_WINDOW sw ON sw.SUBJECT_ID = s.SUBJECT_ID

),
peer AS (
  SELECT
    s.SUBJECT_ID, s.WINDOW_ID, COUNT(*) AS N_PEERS,
    MEDIAN(p.G_PANEL) AS M_PANEL, MEDIAN(p.G_FREQ)  AS M_FREQ,  MEDIAN(p.G_EVENTS) AS M_EVENTS,
    MEDIAN(p.G_LINES) AS M_LINES, MEDIAN(p.G_MIX)   AS M_MIX,   MEDIAN(p.G_UNITS)  AS M_UNITS,
    MEDIAN(p.G_PRICE) AS M_PRICE
  FROM subj s
  JOIN PIH_DECOMP_G p
    ON p.VARIANT = s.VARIANT AND p.PEER_GROUP_KEY = s.PEER_GROUP_KEY AND p.WINDOW_ID = s.WINDOW_ID
   AND p.PROV_BIL_TIN <> s.PROV_BIL_TIN AND p.QUALIFIED_PEER = 1
  GROUP BY 1, 2
),
adj AS (
  SELECT
    s.*,
    COALESCE(p.N_PEERS, 0) AS N_PEERS,
    CASE WHEN COALESCE(p.N_PEERS, 0) >= c.MIN_PEERS THEN 1 ELSE 0 END AS PEER_ADJ_OK,
    CASE WHEN COALESCE(p.N_PEERS, 0) >= c.MIN_PEERS THEN p.M_PANEL  ELSE 0 END AS PG_PANEL,
    CASE WHEN COALESCE(p.N_PEERS, 0) >= c.MIN_PEERS THEN p.M_FREQ   ELSE 0 END AS PG_FREQ,
    CASE WHEN COALESCE(p.N_PEERS, 0) >= c.MIN_PEERS THEN p.M_EVENTS ELSE 0 END AS PG_EVENTS,
    CASE WHEN COALESCE(p.N_PEERS, 0) >= c.MIN_PEERS THEN p.M_LINES  ELSE 0 END AS PG_LINES,
    CASE WHEN COALESCE(p.N_PEERS, 0) >= c.MIN_PEERS THEN p.M_MIX    ELSE 0 END AS PG_MIX,
    CASE WHEN COALESCE(p.N_PEERS, 0) >= c.MIN_PEERS THEN p.M_UNITS  ELSE 0 END AS PG_UNITS,
    CASE WHEN COALESCE(p.N_PEERS, 0) >= c.MIN_PEERS THEN p.M_PRICE  ELSE 0 END AS PG_PRICE
  FROM subj s
  LEFT JOIN peer p ON p.SUBJECT_ID = s.SUBJECT_ID AND p.WINDOW_ID = s.WINDOW_ID
  CROSS JOIN PIH_CONFIG c
),
dollars AS (
  SELECT
    adj.*,
    12 * (A1 - A0) / K                        AS RAW_DELTA_ANNUAL,
    12 * LM_AM * (G_PANEL  - PG_PANEL)        AS ADJ_PANEL,
    12 * LM_AM * (G_FREQ   - PG_FREQ)         AS ADJ_FREQ,
    12 * LM_AM * (G_EVENTS - PG_EVENTS)       AS ADJ_EVENTS,
    12 * LM_AM * (G_LINES  - PG_LINES)        AS ADJ_LINES,
    12 * LM_AM * (G_MIX    - PG_MIX)          AS ADJ_MIX,
    12 * LM_AM * (G_UNITS  - PG_UNITS)        AS ADJ_UNITS,
    12 * LM_AM * (G_PRICE  - PG_PRICE)        AS ADJ_PRICE,
    12 * LM_AM * (PG_PANEL + PG_FREQ + PG_EVENTS + PG_LINES + PG_MIX + PG_UNITS + PG_PRICE) AS PEER_TREND
  FROM adj
)
SELECT
  dollars.*,
  ADJ_EVENTS + ADJ_LINES + ADJ_MIX + ADJ_UNITS AS INTENSITY_ADJ,
  ADJ_PANEL + ADJ_FREQ AS VOLUME_ADJ,
  ADJ_PRICE AS PRICE_ADJ,
  ADJ_PANEL + ADJ_FREQ + ADJ_EVENTS + ADJ_LINES + ADJ_MIX + ADJ_UNITS + ADJ_PRICE AS TOTAL_ADJ,
  RAW_DELTA_ANNUAL
    - (ADJ_PANEL + ADJ_FREQ + ADJ_EVENTS + ADJ_LINES + ADJ_MIX + ADJ_UNITS + ADJ_PRICE + PEER_TREND) AS IDENTITY_RESIDUAL
FROM dollars;
```

### 5.4 Limited-history subjects (level track)

These have no pre period, so compare the subject's level to peers over the last three months. The chain is allowed per member-month `= (E/MM) × (L/E) × (A/L)`, plus `MM/D` as visit frequency.

```sql
-- BLOCK: B12_LEVEL
CREATE OR REPLACE TABLE PIH_LEVEL AS
WITH t AS (
  SELECT
    tw.VARIANT, tw.PEER_GROUP_KEY, tw.PROV_BIL_TIN, tw.WINDOW_ID, tw.A, tw.D, tw.MM, tw.E, tw.L,
    tw.A / NULLIF(tw.MM, 0)        AS APMM,
    tw.MM * 1.0 / NULLIF(tw.D, 0)  AS FREQ,
    tw.E * 1.0 / NULLIF(tw.MM, 0)  AS EVENTS_PMM,
    tw.L * 1.0 / NULLIF(tw.E, 0)   AS LINES_PE,
    tw.A / NULLIF(tw.L, 0)         AS APL
  FROM PIH_TW tw
  WHERE tw.WINDOW_ID = 'LVL' AND tw.PERIOD = 'POST'
),
subj AS (
  SELECT s.SUBJECT_ID, s.ROLE, t.*
  FROM PIH_SUBJECTS s
  JOIN t ON t.VARIANT = s.VARIANT AND t.PEER_GROUP_KEY = s.PEER_GROUP_KEY AND t.PROV_BIL_TIN = s.PROV_BIL_TIN
  WHERE s.METHOD_FAMILY = 'LIMITED_HISTORY'
),
peer AS (
  SELECT
    s.SUBJECT_ID, COUNT(*) AS N_PEERS,
    MEDIAN(p.APMM) AS P50_APMM,
    PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY p.APMM) AS P75_APMM,
    MEDIAN(p.FREQ) AS P50_FREQ, MEDIAN(p.EVENTS_PMM) AS P50_EVENTS_PMM,
    MEDIAN(p.LINES_PE) AS P50_LINES_PE, MEDIAN(p.APL) AS P50_APL
  FROM subj s
  JOIN t p
    ON p.VARIANT = s.VARIANT AND p.PEER_GROUP_KEY = s.PEER_GROUP_KEY AND p.PROV_BIL_TIN <> s.PROV_BIL_TIN
  CROSS JOIN PIH_CONFIG c
  WHERE p.D >= c.PEER_MIN_MEMBERS AND p.A >= c.PEER_MIN_ALLOWED
  GROUP BY 1
)
SELECT
  s.*, p.N_PEERS, p.P50_APMM, p.P75_APMM,
  s.APMM / NULLIF(p.P50_APMM, 0)             AS RATIO_APMM,
  s.FREQ / NULLIF(p.P50_FREQ, 0)             AS RATIO_FREQ,
  s.EVENTS_PMM / NULLIF(p.P50_EVENTS_PMM, 0) AS RATIO_EVENTS,
  s.LINES_PE / NULLIF(p.P50_LINES_PE, 0)     AS RATIO_LINES,
  s.APL / NULLIF(p.P50_APL, 0)               AS RATIO_APL,
  GREATEST(s.APMM - COALESCE(p.P75_APMM, s.APMM), 0) * (s.MM / 3.0) * 12 AS LEVEL_EXCESS_ANNUAL
FROM subj s
LEFT JOIN peer p ON p.SUBJECT_ID = s.SUBJECT_ID;
```

For limited-history subjects, `LEVEL_EXCESS_ANNUAL` plays the role that `INTENSITY_ADJ` plays for standard-history subjects: dollars above the peer 75th percentile of allowed per member-month, at the subject's current patient volume. The `RATIO_*` columns say which link of the chain is high.

### 5.5 Stage 2 is done when

- `ABS(IDENTITY_RESIDUAL) < 1` (dollar) for every decomposable row. Any larger residual is a bug.
- Share of standard-history subjects that are decomposable and have `PEER_ADJ_OK = 1` is reported. Expect it to be high for L1 and L2 peer groups.
- For signals, `RAW_DELTA_ANNUAL` is positive for the large majority. It will not equal upstream's excess (different pre window, different peer method), but compute the correlation between `TOTAL_ADJ` and `UPSTREAM_EXCESS` and report it. A weak or negative correlation means the windows or change-point convention are wrong (check 0.3).

## 6. Stage 3: Benign gates

The purpose of this stage is to close benign step-ups with queries, so that no agent time is spent rediscovering them. Each gate writes rows to `PIH_GATE_RESULTS`. A final step turns those into one disposition per subject.

### 6.1 Actions

| Action | Meaning |
|---|---|
| `HOLD` | Data problem. Exclude from all statistics until resolved |

```sql
  SUM(CASE WHEN MBR_SOURCE = 'LOST'         THEN 1 ELSE 0 END) AS N_LOST,
  SUM(CASE WHEN MBR_SOURCE = 'NEW_TO_PAYER' THEN 1 ELSE 0 END) * 1.0
    / NULLIF(SUM(CASE WHEN MBR_SOURCE IN ('NEW_TO_PAYER', 'NEW_TO_TIN') THEN 1 ELSE 0 END), 0) AS NEW_TO_PAYER_SHARE,
  -- continuing cohort: same members, before and after
  SUM(CASE WHEN MBR_SOURCE = 'CONTINUING' THEN A_PRE  ELSE 0 END) AS CC_A_PRE,
  SUM(CASE WHEN MBR_SOURCE = 'CONTINUING' THEN A_POST ELSE 0 END) AS CC_A_POST,
  SUM(CASE WHEN MBR_SOURCE = 'CONTINUING' THEN MM_PRE  ELSE 0 END) AS CC_MM_PRE,
  SUM(CASE WHEN MBR_SOURCE = 'CONTINUING' THEN MM_POST ELSE 0 END) AS CC_MM_POST,
  -- concentration
  SUM(DLT) AS NET_DELTA,
  SUM(CASE WHEN RN <= 3 THEN DLT ELSE 0 END) AS TOP3_DELTA,
  SUM(CASE WHEN RN <= 3 THEN A_POST ELSE 0 END) / NULLIF(SUM(A_POST), 0) AS TOP3_POST_SHARE,
  -- volume-scheme inputs
  SUM(CASE WHEN MBR_SOURCE IN ('NEW_TO_PAYER', 'NEW_TO_TIN') AND N_DOS_POST = 1 THEN 1 ELSE 0 END) * 1.0
    / NULLIF(SUM(CASE WHEN MBR_SOURCE IN ('NEW_TO_PAYER', 'NEW_TO_TIN') THEN 1 ELSE 0 END), 0) AS ONE_AND_DONE_SHARE
FROM ranked
GROUP BY 1;
```

Monthly series per subject (all months, not just the window), used for spike, dip, and alignment checks.

```sql
-- BLOCK: G04_SUBJECT_MONTH
CREATE OR REPLACE TABLE PIH_SUBJECT_MONTH AS
SELECT
  s.SUBJECT_ID, l.SVC_MONTH,
  SUM(l.ALLOWED) AS ALLOWED,
  COUNT(DISTINCT l.MBR_ID) AS MM
FROM PIH_SUBJECTS s
JOIN PIH_LINES_S l
  ON l.VARIANT = s.VARIANT AND l.PEER_GROUP_KEY = s.PEER_GROUP_KEY AND l.PROV_BIL_TIN = s.PROV_BIL_TIN
GROUP BY 1, 2;

CREATE OR REPLACE TABLE PIH_G_MONTH AS
WITH m AS (
  SELECT
    sm.SUBJECT_ID, sm.SVC_MONTH, sm.ALLOWED, sm.MM, w.K, w.POST_START,
    CASE WHEN sm.SVC_MONTH BETWEEN w.POST_START AND w.POST_END THEN 'POST'
         WHEN sm.SVC_MONTH BETWEEN w.PRE_START AND w.PRE_END THEN 'PRE'
         WHEN sm.SVC_MONTH BETWEEN DATEADD('MONTH', -w.K, w.PRE_START) AND DATEADD('MONTH', -1, w.PRE_START) THEN 'EARLIER'
    END AS PERIOD,
    DATEDIFF('MONTH', w.POST_START, sm.SVC_MONTH) AS REL_MONTH
  FROM PIH_SUBJECT_MONTH sm
  JOIN PIH_SUBJECT_WINDOW sw ON sw.SUBJECT_ID = sm.SUBJECT_ID AND sw.IS_PRIMARY = 1
  JOIN PIH_WINDOWS w ON w.WINDOW_ID = sw.WINDOW_ID
  WHERE w.PRE_START IS NOT NULL
)
SELECT
  SUBJECT_ID, MAX(K) AS K,
  SUM(CASE WHEN PERIOD = 'PRE'     THEN ALLOWED ELSE 0 END) / MAX(K) AS PRE_MEAN,
  SUM(CASE WHEN PERIOD = 'POST'    THEN ALLOWED ELSE 0 END) / MAX(K) AS POST_MEAN,
  SUM(CASE WHEN PERIOD = 'EARLIER' THEN ALLOWED ELSE 0 END) / MAX(K) AS EARLIER_MEAN,
  COUNT(DISTINCT CASE WHEN PERIOD = 'EARLIER' THEN SVC_MONTH END) AS N_EARLIER_MONTHS,
  COUNT(DISTINCT CASE WHEN PERIOD = 'PRE' THEN SVC_MONTH END) AS N_PRE_MONTHS_WITH_DATA,
  (SUM(CASE WHEN PERIOD = 'POST' THEN ALLOWED ELSE 0 END) - MAX(CASE WHEN PERIOD = 'POST' THEN ALLOWED ELSE 0 END))
     / NULLIF(MAX(K) - 1, 0) AS POST_MEAN_EX_MAX,
  -- allowed per active member-month, 3 months each side of the change point
  SUM(CASE WHEN REL_MONTH BETWEEN 0 AND 2   THEN ALLOWED ELSE 0 END)
    / NULLIF(SUM(CASE WHEN REL_MONTH BETWEEN 0 AND 2   THEN MM ELSE 0 END), 0) AS APMM_AFTER3,
  SUM(CASE WHEN REL_MONTH BETWEEN -3 AND -1 THEN ALLOWED ELSE 0 END)
    / NULLIF(SUM(CASE WHEN REL_MONTH BETWEEN -3 AND -1 THEN MM ELSE 0 END), 0) AS APMM_BEFORE3
FROM m
WHERE PERIOD IS NOT NULL
GROUP BY 1;
```

TIN-wide view, to detect dollars that merely moved between cells, par statuses, or platforms. This reads `SRC_CLAIM_LINES` because other cells of the same TIN may be outside scope.

```sql
-- BLOCK: G05_TINWIDE
CREATE OR REPLACE TABLE PIH_SUBJECT_TINWIDE AS
SELECT
  s.SUBJECT_ID,
  CASE WHEN CAST(DATE_TRUNC('MONTH', cl.FDOS_LN) AS DATE) BETWEEN w.POST_START AND w.POST_END
       THEN 'POST' ELSE 'PRE' END AS PERIOD,
  CASE WHEN cl.LOB_CAT = s.LOB_CAT AND cl.HCC_FIX = s.HCC_FIX
        AND cl.SERVICE_CATEGORY = s.SERVICE_CATEGORY THEN 1 ELSE 0 END AS IS_SIGNAL_CELL,
  CASE WHEN (s.VARIANT = 'NONPAR' AND cl.PROV_SVC_PAR_STAT = 'N')
         OR (s.VARIANT = 'PAR' AND cl.PROV_SVC_PAR_STAT = 'P')
         OR (s.VARIANT = 'BH') THEN 1 ELSE 0 END AS IS_VARIANT_PAR,
  cl.PROV_SVC_PAR_STAT, cl.PLATFORM,
  SUM(cl.AMT_ALLOWED) AS ALLOWED
FROM PIH_SUBJECTS s
JOIN PIH_SUBJECT_WINDOW sw ON sw.SUBJECT_ID = s.SUBJECT_ID AND sw.IS_PRIMARY = 1
JOIN PIH_WINDOWS w ON w.WINDOW_ID = sw.WINDOW_ID
JOIN SRC_CLAIM_LINES cl ON cl.PROV_BIL_TIN = s.PROV_BIL_TIN
WHERE w.PRE_START IS NOT NULL
  AND CAST(DATE_TRUNC('MONTH', cl.FDOS_LN) AS DATE) BETWEEN w.PRE_START AND w.POST_END
GROUP BY 1, 2, 3, 4, 5, 6;

CREATE OR REPLACE TABLE PIH_G_STRUCT AS
WITH t AS (
  SELECT
    SUBJECT_ID,
    SUM(CASE WHEN IS_SIGNAL_CELL = 1 AND IS_VARIANT_PAR = 1 AND PERIOD = 'POST' THEN ALLOWED ELSE 0 END)
      - SUM(CASE WHEN IS_SIGNAL_CELL = 1 AND IS_VARIANT_PAR = 1 AND PERIOD = 'PRE' THEN ALLOWED ELSE 0 END) AS CELL_DELTA,
    SUM(CASE WHEN IS_VARIANT_PAR = 1 AND PERIOD = 'POST' THEN ALLOWED ELSE 0 END)
      - SUM(CASE WHEN IS_VARIANT_PAR = 1 AND PERIOD = 'PRE' THEN ALLOWED ELSE 0 END) AS TIN_DELTA,
    SUM(CASE WHEN IS_SIGNAL_CELL = 1 AND PERIOD = 'POST' THEN ALLOWED ELSE 0 END)
      - SUM(CASE WHEN IS_SIGNAL_CELL = 1 AND PERIOD = 'PRE' THEN ALLOWED ELSE 0 END) AS CELL_ALLPAR_DELTA,
    SUM(CASE WHEN IS_SIGNAL_CELL = 1 AND PROV_SVC_PAR_STAT = 'N' AND PERIOD = 'PRE' THEN ALLOWED ELSE 0 END)
      / NULLIF(SUM(CASE WHEN IS_SIGNAL_CELL = 1 AND PERIOD = 'PRE' THEN ALLOWED ELSE 0 END), 0) AS NONPAR_SHARE_PRE,
    SUM(CASE WHEN IS_SIGNAL_CELL = 1 AND PROV_SVC_PAR_STAT = 'N' AND PERIOD = 'POST' THEN ALLOWED ELSE 0 END)
      / NULLIF(SUM(CASE WHEN IS_SIGNAL_CELL = 1 AND PERIOD = 'POST' THEN ALLOWED ELSE 0 END), 0) AS NONPAR_SHARE_POST
  FROM PIH_SUBJECT_TINWIDE
  GROUP BY 1
),
plat AS (
  SELECT SUBJECT_ID, MAX(ABS(SHARE_POST - SHARE_PRE)) AS MAX_PLATFORM_SHARE_SHIFT
  FROM (
    SELECT
      SUBJECT_ID, PLATFORM,
      SUM(CASE WHEN PERIOD = 'PRE' THEN ALLOWED ELSE 0 END)
        / NULLIF(SUM(SUM(CASE WHEN PERIOD = 'PRE' THEN ALLOWED ELSE 0 END)) OVER (PARTITION BY SUBJECT_ID), 0) AS SHARE_PRE,
      SUM(CASE WHEN PERIOD = 'POST' THEN ALLOWED ELSE 0 END)
        / NULLIF(SUM(SUM(CASE WHEN PERIOD = 'POST' THEN ALLOWED ELSE 0 END)) OVER (PARTITION BY SUBJECT_ID), 0) AS SHARE_POST
    FROM PIH_SUBJECT_TINWIDE
    WHERE IS_SIGNAL_CELL = 1 AND IS_VARIANT_PAR = 1
    GROUP BY 1, 2
  ) x
  GROUP BY 1
)
SELECT
  t.*,
  t.TIN_DELTA / NULLIF(t.CELL_DELTA, 0)         AS TIN_TO_CELL_RATIO,
  t.CELL_ALLPAR_DELTA / NULLIF(t.CELL_DELTA, 0) AS ALLPAR_TO_CELL_RATIO,
  COALESCE(t.NONPAR_SHARE_POST, 0) - COALESCE(t.NONPAR_SHARE_PRE, 0) AS NONPAR_SHARE_SHIFT,
  p.MAX_PLATFORM_SHARE_SHIFT
FROM t
LEFT JOIN plat p ON p.SUBJECT_ID = t.SUBJECT_ID;
```

Price behavior per subject: is the price change uniform across items (a fee schedule update) or concentrated in a few, and does allowed track billed charges?

```sql
-- BLOCK: G06_PRICE
CREATE OR REPLACE TABLE PIH_G_PRICE AS
WITH item AS (
  SELECT
    s.SUBJECT_ID, i.ITEM,
    SUM(CASE WHEN i.PERIOD = 'PRE'  THEN i.L_K  ELSE 0 END) AS L0K,
    SUM(CASE WHEN i.PERIOD = 'POST' THEN i.L_K  ELSE 0 END) AS L1K,
    SUM(CASE WHEN i.PERIOD = 'PRE'  THEN i.U_K  ELSE 0 END) AS U0K,
    SUM(CASE WHEN i.PERIOD = 'POST' THEN i.U_K  ELSE 0 END) AS U1K,
    SUM(CASE WHEN i.PERIOD = 'PRE'  THEN i.A_K  ELSE 0 END) AS A0K,
    SUM(CASE WHEN i.PERIOD = 'POST' THEN i.A_K  ELSE 0 END) AS A1K,
    SUM(CASE WHEN i.PERIOD = 'PRE'  THEN i.BL_K ELSE 0 END) AS B0K,
    SUM(CASE WHEN i.PERIOD = 'POST' THEN i.BL_K ELSE 0 END) AS B1K
  FROM PIH_SUBJECTS s
  JOIN PIH_SUBJECT_WINDOW sw ON sw.SUBJECT_ID = s.SUBJECT_ID AND sw.IS_PRIMARY = 1
  JOIN PIH_TW_ITEM i
    ON i.VARIANT = s.VARIANT AND i.PEER_GROUP_KEY = s.PEER_GROUP_KEY
   AND i.PROV_BIL_TIN = s.PROV_BIL_TIN AND i.WINDOW_ID = sw.WINDOW_ID
  GROUP BY 1, 2
),
r AS (
  SELECT
    SUBJECT_ID, ITEM, A1K,
    (A1K / NULLIF(U1K, 0)) / NULLIF(A0K / NULLIF(U0K, 0), 0) AS PRICE_RATIO,
    (B1K / NULLIF(U1K, 0)) / NULLIF(B0K / NULLIF(U0K, 0), 0) AS CHARGE_RATIO
  FROM item
  WHERE L0K >= 20 AND L1K >= 20
),
tot AS (SELECT SUBJECT_ID, SUM(A1K) AS A1_ALL, SUM(A1K) / NULLIF(SUM(B1K), 0) AS ALLOWED_TO_BILLED_POST FROM item GROUP BY 1)
SELECT
  r.SUBJECT_ID,
  COUNT(*) AS N_COMPARABLE_ITEMS,
  SUM(r.A1K) / NULLIF(MAX(tot.A1_ALL), 0) AS COMPARABLE_DOLLAR_SHARE,
  PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY r.PRICE_RATIO) AS PRICE_RATIO_P25,
  MEDIAN(r.PRICE_RATIO) AS PRICE_RATIO_P50,
  PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY r.PRICE_RATIO) AS PRICE_RATIO_P75,
  MEDIAN(r.CHARGE_RATIO) AS CHARGE_RATIO_P50,
  MAX(tot.ALLOWED_TO_BILLED_POST) AS ALLOWED_TO_BILLED_POST
FROM r
JOIN tot ON tot.SUBJECT_ID = r.SUBJECT_ID
GROUP BY 1;
```

### 6.3 Gate catalog

Every check to implement. "Subject" means signal or control. Unless stated, a check uses the primary window.

#### Group A: data artifacts

| ID | Label | What it catches | Logic | Action |
|---|---|---|---|---|
| A1 | `RECON_MISMATCH` | Line-level data does not reproduce the series the signal was computed on | Stage 0.4 comparison, per subject: monthly allowed differs from upstream by more than 5% in over a quarter of months | `HOLD` |
| A2 | `ADJUSTMENT_ARTIFACT` | Step-up created by reversals or adjustments posting unevenly | Compute the pre-to-post delta on raw positive rows of `SRC_CLAIM_LINES` (`AMT_ALLOWED > 0`, no netting). Fire if the netted delta (`A1 − A0` in `PIH_DECOMP_G`) is at most 50% of the raw delta | `CLOSE_ARTIFACT` |
| A3 | `GRAIN_RESHUFFLE` | Dollars moved from another cell of the same TIN (service category or LOB reassignment) | `PIH_G_STRUCT.TIN_TO_CELL_RATIO ≤ 0.25` (TIN-wide change is at most a quarter of the cell's change). Then check item overlap: among items that grew in the signal cell, at least 50% of their growth dollars are in codes that shrank in the TIN's other cells | Both true: `CLOSE_ARTIFACT`. Ratio only: `FLAG` as `SUBSTITUTION` (real shift toward a costlier category) |
| A4 | `PAR_STATUS_FLIP` | TIN joined or left the network, so dollars moved between the par and non-par models | `ABS(NONPAR_SHARE_SHIFT) ≥ 0.30` and `ALLPAR_TO_CELL_RATIO ≤ 0.25` | `PAR` variant: `CLOSE_ARTIFACT`. `NONPAR` variant: `FLAG` as `WENT_OUT_OF_NETWORK`, never close |
| A5 | `BH_PAR_MIX_SHIFT` | BH model pools par statuses, so a shift toward non-par raises allowed per unit | `BH` variant and `ABS(NONPAR_SHARE_SHIFT) ≥ 0.20` | `FLAG` |
| A6 | `PLATFORM_SHIFT` | Claims moved between COSMOS, UNET, CSP | `MAX_PLATFORM_SHARE_SHIFT ≥ 0.30` | `FLAG`. Pass platform shares to Stage 6; a platform move can expose an edit gap |
| A7 | `ONE_MONTH_SPIKE` | The post period is one big month, not a sustained shift | `POST_MEAN ≥ 1.15 × PRE_MEAN` (there is a step) and `POST_MEAN_EX_MAX ≤ 1.10 × PRE_MEAN` (it vanishes without the top month), from `PIH_G_MONTH` | `STANDARD_HISTORY` in `PAR` or `BH`: `CLOSE_ARTIFACT`. `NONPAR`: `FLAG` (burst billing can be deliberate) |
| A8 | `HIGH_COST_MEMBERS` | A handful of catastrophic cases | `TOP3_DELTA ≥ 0.60 × NET_DELTA` and `TOP3_POST_SHARE ≥ 0.20` (from `PIH_G_MBR`), and A9 did not fire | `CLOSE_ARTIFACT` |
| A9 | `OUTLIER_LINE` | A single line large enough to move the series, often a units keying error | Any netted post-period line with `ALLOWED ≥ 20%` of the subject's `A1 − A0`, or with `UNITS_ADJ ≥ 10 ×` that item's scope-wide median units and `ALLOWED ≥ 10,000` | `FLAG`. Also write the line to a separate "claim-level review" list: these are recovery leads, not concepts |
| A10 | `PRE_DIP_RECOVERY` | The pre period was abnormally low (held claims, a billing gap), so "post" is a return to normal | `N_EARLIER_MONTHS = K` and `PRE_MEAN < 0.70 × EARLIER_MEAN` and `POST_MEAN ≤ 1.15 × EARLIER_MEAN` | `CLOSE_ARTIFACT` |
| A11 | `PRE_GAPS` | Months with no billing inside the pre window | `N_PRE_MONTHS_WITH_DATA < K` | `FLAG` |
| A12 | `TABLE_BOUNDARY` | The whole increase sits in months that come from a different source table | Compute the post mean separately for months in each source table (check 0.12). Fire if months from the earlier table are within 10% of `PRE_MEAN` and all the increase is in the later table's months | `INFO`. Read together with price gates: a January fee schedule looks identical |

#### Group V: volume

| ID | Label | What it catches | Logic | Action |
|---|---|---|---|---|
| V1 | `PANEL_DOMINANT` | Step-up is mostly more patients | `VOLUME_ADJ ≥ 0.70 × TOTAL_ADJ` and `TOTAL_ADJ > 0` | `LABEL` |
| V2 | `MEMBERSHIP_GROWTH` | The new patients are new to the plan | `NEW_TO_PAYER_SHARE ≥ 0.60` and V1 fired | `LABEL` |
| V3 | `TIN_MIGRATION` | New patients came in bulk from one other TIN: a merger, acquisition, or tax ID change | Among `NEW_TO_TIN` members (need at least 20), find each member's most recent other TIN in the same cell during the 12 months before `POST_START` (query `SRC_CLAIM_LINES`). Fire if one donor TIN accounts for at least 50% of them and the donor's allowed in the cell fell at least 50% pre to post | `LABEL` |
| V3b | `MIGRATION_WITH_UPLIFT` | The acquired patients now cost more per month than they did at the old TIN | For the inherited members: allowed per active member-month at the subject (post) divided by the same at the donor (pre) is at least 1.25 | `FLAG`. This is a classic concept: same patients, same doctors, higher billing after acquisition |
| V4 | `PROVIDER_ACQUISITION` | Clinicians moved in from another TIN (only if rendering NPI exists) | At least 50% of post dollars are rendered by NPIs that billed under a different TIN in the pre period and never under this TIN before | `LABEL`, plus the V3b uplift test per NPI |
| V5 | `LOCAL_MARKET_GROWTH` | Membership grew in this provider's market. Upstream peer groups have no geography | Preferred: if a geography column exists, compare panel growth to same-cell TINs in the same state or market. Otherwise define local peers as the 20 TINs in the same cell that share the most members with the subject (at least 10 shared). Fire if their median `ln(D1/D0)` over the subject's window is at least 70% of the subject's `G_PANEL` | `LABEL` |
| V6a | `ONE_AND_DONE` | Many new patients seen exactly once at high cost | `ONE_AND_DONE_SHARE ≥ 0.40` and the subject's allowed per member (`A1 / D1`) is at or above the peer 75th percentile | `FLAG` |
| V6b | `SHARED_ROSTER` | The same patients appear at several flagged providers | At least 20% of the subject's post-period members also appear in the post period of another **signal** subject that is in a different TIN group | `FLAG` |
| V6c | `BATCH_ONSET` | New patients arrive on a few dates: screening events, bulk enrollment | At least 30% of new members have `FIRST_POST_DOS` on the three most common dates | `FLAG` |
| V6d | `RAMP_OUTLIER` | Panel growth far beyond anything peers show | `G_PANEL` at or above the 99th percentile of `G_PANEL` among qualified peers | `FLAG` |
| V7 | `FREQUENCY_ESCALATION` | The same patients are being brought back in more months than before | From `PIH_G_MBR`: `N_CONTINUING ≥ 20` and `CC_MM_POST / CC_MM_PRE ≥ 1.15`, and that ratio is at or above the 90th percentile of the same ratio among qualified peers (compute it for peer TINs the same way) | `FLAG` always. Measured on continuing patients so that panel churn cannot cause it |

Run V6a–V6d for every subject in the `NONPAR` and `BH` variants and every limited-history subject. In those populations, more patients can be the scheme.

#### Group P: price

| ID | Label | What it catches | Logic | Action |
|---|---|---|---|---|
| P1 | `PRICE_DOMINANT` | Step-up is mostly a rate change | `ADJ_PRICE ≥ 0.70 × TOTAL_ADJ` and `TOTAL_ADJ > 0` | `LABEL` |
| P2 | `UNIFORM_RATE_UPDATE` | An across-the-board fee schedule or contract escalator | From `PIH_G_PRICE`: `COMPARABLE_DOLLAR_SHARE ≥ 0.50`, `ABS(PRICE_RATIO_P50 − 1) ≥ 0.02`, and both P25 and P75 within 0.03 of P50 | `LABEL` |
| P3 | `SELECTIVE_RATE_CHANGE` | Price moved on a few items only: a carve-out, or a contract loaded wrongly | P1 fired, P2 did not, and three or fewer items account for at least 70% of the subject's `PRICE_TERM` | `FLAG` |
| P4 | `PAYER_SIDE_REPRICING` | Allowed rose but billed charges did not: the change is on the payer's side | `PRICE_RATIO_P50 ≥ 1.03` and `ABS(CHARGE_RATIO_P50 − 1) ≤ 0.01` | `PAR`: `LABEL`. `NONPAR`: `FLAG` (out-of-network repricing or dispute outcomes; different business owner) |
| P5 | `CHARGE_INFLATION` | Allowed tracks billed charges, and charges went up | `CHARGE_RATIO_P50 ≥ 1.05` and `ABS(PRICE_RATIO_P50 / CHARGE_RATIO_P50 − 1) ≤ 0.02` | `FLAG` always. Charge increases on percent-of-charge terms are a real concept |
| P6 | `NONPAR_RATE_SHIFT` | Any price-dominant step-up out of network | `NONPAR` variant and P1 fired | `FLAG`, never close |
| P7 | `COST_SHARE_SHIFT` | Paid-to-allowed ratio moved, so allowed dollars overstate or understate what the plan pays | `ABS(PD1/A1 − PD0/A0) ≥ 0.10` | `INFO`. Size in paid dollars as well |

#### Group S: structure and mix

| ID | Label | What it catches | Logic | Action |
|---|---|---|---|---|
| S1 | `COMMON_NEW_SERVICE` | The provider started offering something peers commonly offer, at normal levels | Using Stage 4 output for `P1` tokens: patterns with `NEW_TO_TIN = 1`, `PEER_PREV_POST ≥ 0.30`, and `LEVEL_RATIO ≤ 1.5`. Sum their `EXCESS_ANNUAL` as `COMMON_NEW_SERVICE_USD` | `LABEL`, and subtract `COMMON_NEW_SERVICE_USD` from intensity when applying the dollar threshold in 6.5 |
| S2 | `CODESET_TURNOVER` | Dollars moved from retired codes to their replacements | Build a code lifespan table from `PIH_LINES`: first and last month each `CODE` is billed by at least 5 TINs. A code is "born" if its first month is within 3 months before `POST_START` or later, "retired" if its last month is before `POST_END`. Sum `EXCESS_ANNUAL` of born-code patterns as `CODESET_USD` | `LABEL`, and subtract `CODESET_USD` from intensity in 6.5. Tag those patterns `NEW_CODE` for Stage 5 |
| S3 | `SITE_OF_SERVICE_SHIFT` | Services moved between office and facility settings, or professional and facility claim types | Share of allowed by `SITE`, and separately by `CLM_TYPE`, changes by at least 0.20 for any value | `FLAG` always. Conversion to facility billing is a known concept |
| S4 | `TAXONOMY_SHIFT` | The TIN's dominant specialty changed, so its peer group no longer fits | Dominant taxonomy by allowed dollars differs between pre and post windows | `FLAG` as weak peers |
| S5 | `WEAK_PEERS` | Peer comparison is coarse | `PEER_GROUP_LEVEL = 'L3'` or `PEER_ADJ_OK = 0` | `FLAG`. Rank these in a separate lower tier |

#### Group R: robustness

| ID | Label | What it catches | Logic | Action |
|---|---|---|---|---|
| R1 | `WINDOW_SENSITIVE` | Result depends on which pre window is used (seasonality) | `INTENSITY_ADJ` under `ADJ` and `YOY` have opposite signs, or their ratio is outside 0.5 to 2 | `FLAG` |
| R2 | `SMALL_BASE` | Pre period too thin to decompose reliably | `D0 < 10` or `A0 < 5,000`, or not decomposable | Route to the level track (5.4) using the `LVL` window |
| R3 | `PM_JUMP_ALIGNED` | Does spend per patient actually jump at the upstream change point? | `APMM_AFTER3 / APMM_BEFORE3 ≥ 1.10` | `INFO`, stored as yes or no. Report the share of signals where it is "no": that measures how often upstream's date is driven by patient count alone |
| R4 | `CC_CONFIRMS` | Do the same patients cost more after than before? | `CC_A_POST > CC_A_PRE` and `N_CONTINUING ≥ 10` | `INFO`. Continuing patients usually cost less over time, so a rise here is strong corroboration of intensity |

### 6.4 Writing gate results

One row per gate that fires. Example for three gates; implement the rest the same way from the catalog.

```sql
-- BLOCK: G07_GATE_RESULTS
CREATE OR REPLACE TABLE PIH_GATE_RESULTS (
  SUBJECT_ID VARCHAR, GATE_ID VARCHAR, LABEL VARCHAR, ACTION VARCHAR, METRIC_VALUE DOUBLE, DETAIL VARCHAR
);

-- A7 one-month spike
INSERT INTO PIH_GATE_RESULTS
SELECT g.SUBJECT_ID, 'A7', 'ONE_MONTH_SPIKE',
       CASE WHEN s.VARIANT = 'NONPAR' THEN 'FLAG' ELSE 'CLOSE_ARTIFACT' END,
       g.POST_MEAN_EX_MAX / NULLIF(g.PRE_MEAN, 0), 'post mean excluding top month / pre mean'
FROM PIH_G_MONTH g
JOIN PIH_SUBJECTS s ON s.SUBJECT_ID = g.SUBJECT_ID
WHERE g.POST_MEAN >= 1.15 * g.PRE_MEAN AND g.POST_MEAN_EX_MAX <= 1.10 * g.PRE_MEAN;

-- A8 high-cost members
INSERT INTO PIH_GATE_RESULTS
SELECT SUBJECT_ID, 'A8', 'HIGH_COST_MEMBERS', 'CLOSE_ARTIFACT', TOP3_DELTA / NULLIF(NET_DELTA, 0), 'top-3 member share of net delta'
FROM PIH_G_MBR
WHERE NET_DELTA > 0 AND TOP3_DELTA >= 0.60 * NET_DELTA AND TOP3_POST_SHARE >= 0.20;

-- V1 panel dominant, P1 price dominant
INSERT INTO PIH_GATE_RESULTS
SELECT SUBJECT_ID, 'V1', 'PANEL_DOMINANT', 'LABEL', VOLUME_ADJ / NULLIF(TOTAL_ADJ, 0), 'volume share of adjusted total'
FROM PIH_DECOMP
WHERE IS_PRIMARY = 1 AND DECOMPOSABLE = 1 AND TOTAL_ADJ > 0 AND VOLUME_ADJ >= 0.70 * TOTAL_ADJ;

INSERT INTO PIH_GATE_RESULTS
SELECT SUBJECT_ID, 'P1', 'PRICE_DOMINANT', 'LABEL', ADJ_PRICE / NULLIF(TOTAL_ADJ, 0), 'price share of adjusted total'
FROM PIH_DECOMP
WHERE IS_PRIMARY = 1 AND DECOMPOSABLE = 1 AND TOTAL_ADJ > 0 AND ADJ_PRICE >= 0.70 * TOTAL_ADJ;
```

### 6.5 Disposition

Applied in this order:

1. Any `HOLD` → `HOLD`.
2. Any `CLOSE_ARTIFACT` → `CLOSED_ARTIFACT`.
3. Net intensity (`INTENSITY_ADJ` minus `COMMON_NEW_SERVICE_USD` and `CODESET_USD`; for limited history, `LEVEL_EXCESS_ANNUAL`) at or above `MIN_INTENSITY_USD` → `PASS`. A subject can be 80% panel growth and still pass here: the residual is what matters.
4. Any `FLAG` → `PASS_FLAGGED`. Stage 6 must address the flag specifically.
5. Otherwise → `CLOSED_BENIGN`, with primary reason = the largest of volume and price, or `BELOW_THRESHOLD` if neither label fired.

Gates S1 and S2 need Stage 4 output. Run Stage 4 for all subjects not already closed as artifacts, then finalize dispositions.

```sql
-- BLOCK: G08_DISPOSITION
CREATE OR REPLACE TABLE PIH_GATES AS
WITH agg AS (
  SELECT
    SUBJECT_ID,
    MAX(CASE WHEN ACTION = 'HOLD' THEN 1 ELSE 0 END) AS HAS_HOLD,
    MAX(CASE WHEN ACTION = 'CLOSE_ARTIFACT' THEN 1 ELSE 0 END) AS HAS_ARTIFACT,
    MAX(CASE WHEN ACTION = 'FLAG' THEN 1 ELSE 0 END) AS HAS_FLAG,
    MAX(CASE WHEN LABEL IN ('PANEL_DOMINANT', 'MEMBERSHIP_GROWTH', 'TIN_MIGRATION', 'PROVIDER_ACQUISITION', 'LOCAL_MARKET_GROWTH') THEN 1 ELSE 0 END) AS HAS_VOLUME,
    MAX(CASE WHEN LABEL IN ('PRICE_DOMINANT', 'UNIFORM_RATE_UPDATE', 'PAYER_SIDE_REPRICING') THEN 1 ELSE 0 END) AS HAS_PRICE,
    SUM(CASE WHEN LABEL IN ('COMMON_NEW_SERVICE', 'CODESET_TURNOVER') THEN METRIC_VALUE ELSE 0 END) AS BENIGN_MIX_USD,
    LISTAGG(DISTINCT LABEL, ',') AS LABELS
  FROM PIH_GATE_RESULTS
  GROUP BY 1
),
amt AS (
  SELECT s.SUBJECT_ID, s.ROLE, s.METHOD_FAMILY,
         COALESCE(d.INTENSITY_ADJ, lv.LEVEL_EXCESS_ANNUAL, 0) AS INTENSITY_USD,
         d.VOLUME_ADJ, d.PRICE_ADJ, d.TOTAL_ADJ, d.PEER_TREND, d.RAW_DELTA_ANNUAL
  FROM PIH_SUBJECTS s
  LEFT JOIN PIH_DECOMP d ON d.SUBJECT_ID = s.SUBJECT_ID AND d.IS_PRIMARY = 1 AND d.DECOMPOSABLE = 1
  LEFT JOIN PIH_LEVEL lv ON lv.SUBJECT_ID = s.SUBJECT_ID
)
SELECT
  a.*,
  COALESCE(g.LABELS, '') AS LABELS,
  a.INTENSITY_USD - COALESCE(g.BENIGN_MIX_USD, 0) AS NET_INTENSITY_USD,
  CASE
    WHEN COALESCE(g.HAS_HOLD, 0) = 1 THEN 'HOLD'
    WHEN COALESCE(g.HAS_ARTIFACT, 0) = 1 THEN 'CLOSED_ARTIFACT'
    WHEN a.INTENSITY_USD - COALESCE(g.BENIGN_MIX_USD, 0) >= c.MIN_INTENSITY_USD THEN 'PASS'
    WHEN COALESCE(g.HAS_FLAG, 0) = 1 THEN 'PASS_FLAGGED'
    ELSE 'CLOSED_BENIGN'
  END AS DISPOSITION,
  CASE
    WHEN COALESCE(g.HAS_HOLD, 0) = 1 OR COALESCE(g.HAS_ARTIFACT, 0) = 1 THEN NULL
    WHEN a.INTENSITY_USD - COALESCE(g.BENIGN_MIX_USD, 0) >= c.MIN_INTENSITY_USD THEN NULL
    WHEN COALESCE(g.HAS_FLAG, 0) = 1 THEN NULL
    WHEN COALESCE(g.HAS_VOLUME, 0) = 1 AND COALESCE(a.VOLUME_ADJ, 0) >= COALESCE(a.PRICE_ADJ, 0) THEN 'VOLUME'
    WHEN COALESCE(g.HAS_PRICE, 0) = 1 THEN 'PRICE'
    WHEN COALESCE(g.HAS_VOLUME, 0) = 1 THEN 'VOLUME'
    ELSE 'BELOW_THRESHOLD'
  END AS BENIGN_REASON   -- populated only for CLOSED_BENIGN
FROM amt a
LEFT JOIN agg g ON g.SUBJECT_ID = a.SUBJECT_ID
CROSS JOIN PIH_CONFIG c;
```

### 7.2 Pattern excess

The formula mirrors upstream's excess, applied per pattern and per active member-month so that patient growth cannot inflate it:

```
x0, x1      = subject's allowed on the pattern per active member-month, pre and post
PX0, PX1    = the same for all peers pooled, excluding the subject
peer growth = PX1 / PX0 − 1, capped to [−50%, +100%]; set to 0 if peer support is thin
expected    = x0 × (1 + peer growth)
excess      = (x1 − expected) × post active member-months per month × 12
```

**What this number is, and is not.** Pattern excess is the growth in dollars *carrying* the pattern, beyond what peers would predict. It is a detection statistic and an upper bound. It is not the size of a concept: nested tokens count the same dollars several times, a modifier pattern carries the full allowed of the line it sits on, and an `E1` pair carries the dollars of both codes even if one of them would have been billed anyway. Use it to rank and to find recurrence. Sizing happens in Stage 6.

For a pattern the subject did not bill before (`NEW_TO_TIN`), expected is zero and the whole post level is excess. `LEVEL_RATIO = x1 / PX1` and `PEER_PREV_POST` (share of peer TINs billing it) say whether that new pattern is ordinary among peers. For limited-history subjects (`LVL` window) the excess is the level above peers: `x1 − PX1`.

```sql
-- BLOCK: B14_SUBJECT_PATTERN
CREATE OR REPLACE TABLE PIH_SUBJECT_PATTERN AS
WITH wide AS (
  SELECT
    VARIANT, PEER_GROUP_KEY, PROV_BIL_TIN, WINDOW_ID, TOKEN_TYPE, PATTERN_KEY,
    SUM(CASE WHEN PERIOD = 'PRE'  THEN A_P ELSE 0 END) AS A0P,
    SUM(CASE WHEN PERIOD = 'POST' THEN A_P ELSE 0 END) AS A1P,
    SUM(CASE WHEN PERIOD = 'PRE'  THEN L_P ELSE 0 END) AS L0P,
    SUM(CASE WHEN PERIOD = 'POST' THEN L_P ELSE 0 END) AS L1P,
    SUM(CASE WHEN PERIOD = 'PRE'  THEN U_P ELSE 0 END) AS U0P,
    SUM(CASE WHEN PERIOD = 'POST' THEN U_P ELSE 0 END) AS U1P,
    MAX(CASE WHEN PERIOD = 'POST' THEN MBR_P ELSE 0 END) AS MBR1P
  FROM PIH_TW_PATTERN
  GROUP BY 1, 2, 3, 4, 5, 6
),
grp AS (
  SELECT
    VARIANT, PEER_GROUP_KEY, WINDOW_ID, TOKEN_TYPE, PATTERN_KEY,
    SUM(A0P) AS GA0P, SUM(A1P) AS GA1P,
    SUM(CASE WHEN A0P > 0 THEN 1 ELSE 0 END) AS GN0P,
    SUM(CASE WHEN A1P > 0 THEN 1 ELSE 0 END) AS GN1P
  FROM wide
  GROUP BY 1, 2, 3, 4, 5
),
tw AS (
  SELECT
    VARIANT, PEER_GROUP_KEY, PROV_BIL_TIN, WINDOW_ID,
    SUM(CASE WHEN PERIOD = 'PRE'  THEN MM ELSE 0 END) AS MM0,
    SUM(CASE WHEN PERIOD = 'POST' THEN MM ELSE 0 END) AS MM1
  FROM PIH_TW
  GROUP BY 1, 2, 3, 4
),
gtw AS (
  SELECT VARIANT, PEER_GROUP_KEY, WINDOW_ID, SUM(MM0) AS GMM0, SUM(MM1) AS GMM1, COUNT(*) AS GN_TINS
  FROM tw
  GROUP BY 1, 2, 3
),
calc AS (
  SELECT
    s.SUBJECT_ID, s.ROLE, sw.WINDOW_ID, sw.WINDOW_TYPE, sw.IS_PRIMARY, win.K,
    x.TOKEN_TYPE, x.PATTERN_KEY, x.A0P, x.A1P, x.L0P, x.L1P, x.U0P, x.U1P, x.MBR1P,
    t.MM0, t.MM1,
    x.A0P / NULLIF(t.MM0, 0) AS X0,
    x.A1P / NULLIF(t.MM1, 0) AS X1,
    (g.GA0P - x.A0P) / NULLIF(gt.GMM0 - t.MM0, 0) AS PX0,
    (g.GA1P - x.A1P) / NULLIF(gt.GMM1 - t.MM1, 0) AS PX1,
    g.GA0P - x.A0P AS PEER_A0P,
    g.GN0P - CASE WHEN x.A0P > 0 THEN 1 ELSE 0 END AS PEER_N0P,
    (g.GN1P - CASE WHEN x.A1P > 0 THEN 1 ELSE 0 END) * 1.0 / NULLIF(gt.GN_TINS - 1, 0) AS PEER_PREV_POST
  FROM PIH_SUBJECTS s
  JOIN PIH_SUBJECT_WINDOW sw ON sw.SUBJECT_ID = s.SUBJECT_ID
  JOIN PIH_WINDOWS win ON win.WINDOW_ID = sw.WINDOW_ID
  JOIN wide x
    ON x.VARIANT = s.VARIANT AND x.PEER_GROUP_KEY = s.PEER_GROUP_KEY
   AND x.PROV_BIL_TIN = s.PROV_BIL_TIN AND x.WINDOW_ID = sw.WINDOW_ID
  JOIN grp g
    ON g.VARIANT = x.VARIANT AND g.PEER_GROUP_KEY = x.PEER_GROUP_KEY AND g.WINDOW_ID = x.WINDOW_ID
   AND g.TOKEN_TYPE = x.TOKEN_TYPE AND g.PATTERN_KEY = x.PATTERN_KEY
  JOIN tw t
    ON t.VARIANT = x.VARIANT AND t.PEER_GROUP_KEY = x.PEER_GROUP_KEY
   AND t.PROV_BIL_TIN = x.PROV_BIL_TIN AND t.WINDOW_ID = x.WINDOW_ID
  JOIN gtw gt
    ON gt.VARIANT = x.VARIANT AND gt.PEER_GROUP_KEY = x.PEER_GROUP_KEY AND gt.WINDOW_ID = x.WINDOW_ID
),
gr AS (
  SELECT
    calc.*,
    CASE WHEN PEER_A0P >= c.PATTERN_PEER_MIN_ALLOWED AND PEER_N0P >= c.PATTERN_PEER_MIN_TINS AND PX0 > 0
         THEN LEAST(GREATEST(COALESCE(PX1, 0) / PX0 - 1, -0.5), 1.0) ELSE 0 END AS PEER_GROWTH,
    CASE WHEN WINDOW_TYPE = 'LVL' THEN NULL     -- no pre period, so peer growth is not used
         WHEN PEER_A0P >= c.PATTERN_PEER_MIN_ALLOWED AND PEER_N0P >= c.PATTERN_PEER_MIN_TINS AND PX0 > 0
         THEN 0 ELSE 1 END AS PEER_THIN
  FROM calc
  CROSS JOIN PIH_CONFIG c
),
ex AS (
  SELECT
    gr.*,
    CASE WHEN WINDOW_TYPE = 'LVL' THEN COALESCE(X1, 0) - COALESCE(PX1, 0)
         ELSE COALESCE(X1, 0) - COALESCE(X0, 0) * (1 + PEER_GROWTH) END AS EXCESS_PMPM
  FROM gr
)
SELECT
  ex.*,
  EXCESS_PMPM * (MM1 * 1.0 / K) * 12 AS EXCESS_ANNUAL,
  CASE WHEN A0P = 0 AND WINDOW_TYPE <> 'LVL' THEN 1 ELSE 0 END AS NEW_TO_TIN,
  X1 / NULLIF(PX1, 0) AS LEVEL_RATIO,
  -- is the excess price only? lines and units per member-month flat while allowed per unit rose
  CASE WHEN A0P > 0 AND L0P > 0 AND MM0 > 0 AND MM1 > 0
        AND ABS((U1P * 1.0 / MM1) / NULLIF(U0P * 1.0 / MM0, 0) - 1) <= 0.10
        AND (A1P / NULLIF(U1P, 0)) / NULLIF(A0P / NULLIF(U0P, 0), 0) >= 1.03 THEN 1 ELSE 0 END AS PRICE_ONLY
FROM ex;
```

### 7.3 What counts as a candidate at one subject

A row of `PIH_SUBJECT_PATTERN` is a candidate if, on the primary window:

- `EXCESS_ANNUAL ≥ MIN_PATTERN_EXCESS_USD`
- `L1P ≥ MIN_PATTERN_LINES` and `MBR1P ≥ MIN_PATTERN_MEMBERS`
- `PRICE_ONLY = 0`, unless the subject is in the `NONPAR` variant

There is deliberately no per-subject significance test. A single subject's pattern list is noisy by nature. The noise filter is the next stage: a pattern has to show up independently at several unrelated TINs.

### 7.4 Within-family mix (upcoding detector)

Upcoding is a shift toward higher-paying codes inside one family of services, with total volume in the family unchanged. To isolate it, for each subject and each `AHRQ_CAT` family `f`:

```
family line share        W_f = Σ_{k in f} w_k
family allowed per line  a_f = Σ_{k in f} (w_k / W_f) · u_k · p_k
within_f = Σ_{k in f} avg(u_k·p_k) · (w_k1 − w_k0)  −  avg(a_f) · (W_f1 − W_f0)
```

`within_f` is the part of the mix term caused by shifting between codes inside family `f`. Convert to dollars the same way as the main decomposition (`12 × LM_AM × within_f / LM_APL`), and peer-adjust by subtracting the peer median of `within_f / LM_APL` among peers with at least 30 lines in the family in both periods. Store results as token type `W1` with `PATTERN_KEY = AHRQ_CAT`, and include them in Stage 5 like any other pattern. Reuse the `item2` logic from block B10 with `AHRQ_CAT` carried alongside `ITEM`.

### 7.5 Stage 4 is done when

- For 10 random subjects with a material step-up, `SUM(EXCESS_ANNUAL)` over their `P1` rows is within roughly 25% of `TOTAL_ADJ − VOLUME_ADJ` from `PIH_DECOMP`. The two are computed differently (pooled peers per pattern versus median peers per component), so they will not match exactly, but they should be the same order of magnitude and sign.
- The share of pattern rows with `PEER_THIN = 1` is reported by token type.

## 8. Stage 5: Pivot from providers to patterns

### 8.1 TIN groups

Two TINs carrying the same pattern only count as independent evidence if they are unrelated. Build an edge between two TINs if any of these holds:

1. **Shared members:** the Jaccard overlap of their post-period member sets, across all in-scope cells, is at least 0.20.
2. **Shared clinicians** (if `RENDERING_NPI` exists): at least one NPI accounts for 10% or more of dollars at both.
3. **Migration link:** gate V3 or V4 identified one as the donor of the other.

Then take connected components. Edges in SQL, components in Python:

```sql
-- SKETCH (not executed): shared-member edges among TINs that carry any candidate pattern

  SELECT DISTINCT s.PROV_BIL_TIN
  FROM PIH_SUBJECT_PATTERN sp JOIN PIH_SUBJECTS s ON s.SUBJECT_ID = sp.SUBJECT_ID
```

```python
# Connected components -> PIH_TIN_GROUP(PROV_BIL_TIN, TIN_GROUP_ID)
def tin_groups(tins, edges):
    parent = {t: t for t in tins}
    def find(x):
        while parent[x] != x:
            parent[x] = parent[parent[x]]
            x = parent[x]
        return x
    for a, b in edges:
        ra, rb = find(a), find(b)
        if ra != rb:
            parent[max(ra, rb)] = min(ra, rb)
    return {t: find(t) for t in tins}
```

A TIN with no edges is its own group.

```sql
    COUNT(DISTINCT CASE WHEN ROLE = 'SIGNAL' THEN LOB_CAT END) AS N_LOBS,
    COUNT(DISTINCT CASE WHEN ROLE = 'SIGNAL' THEN PEER_GROUP_KEY END) AS N_PEER_GROUPS,
    AVG(CASE WHEN ROLE = 'SIGNAL' THEN NEW_TO_TIN END) AS SHARE_NEW_TO_TIN,
    MEDIAN(CASE WHEN ROLE = 'SIGNAL' THEN LEVEL_RATIO END) AS MEDIAN_LEVEL_RATIO,
    AVG(CASE WHEN ROLE = 'SIGNAL' THEN PEER_PREV_POST END) AS AVG_PEER_PREV_POST
  FROM cand
  GROUP BY 1, 2
)
SELECT
  a.*,
  COALESCE(g.N_INDEP_GROUPS, 0) AS N_INDEP_GROUPS,
  g.TOP_GROUP_SHARE,
  ((a.N_SIGNAL_SUBJ + 0.5) / (n.N_SIG + 1.0)) / ((a.N_CONTROL_SUBJ + 0.5) / (n.N_CTL + 1.0)) AS ENRICHMENT,
  CASE WHEN COALESCE(g.N_INDEP_GROUPS, 0) >= c.MIN_INDEP_GROUPS
        AND g.TOP_GROUP_SHARE <= c.MAX_TOP_GROUP_SHARE THEN 1 ELSE 0 END AS IS_RECURRING
FROM agg a
LEFT JOIN grp2 g ON g.TOKEN_TYPE = a.TOKEN_TYPE AND g.PATTERN_KEY = a.PATTERN_KEY
CROSS JOIN n
CROSS JOIN PIH_CONFIG c;
```

`ENRICHMENT` is how much more often a pattern is a candidate among signals than among controls, with a small-count correction. Above about 2 means the signals are pointing at it; near 1 means it is everywhere.

### 8.3 Merging redundant patterns

Tokens are nested (`P3` inside `P2` inside `P1`; `P4`, `P5`, `M1` inside `P1`), so one real pattern appears several times. Among recurring patterns:

1. For each child and its parent (the parent key is the child key truncated at the last `|` for `P2`, `P3`; the code alone for `P4`, `P5`, `M1`): if the child carries at least 80% of the parent's `SIGNAL_EXCESS_ANNUAL`, drop the parent. The more specific description wins.
2. If a child carries less than 30% of its parent's excess, drop the child.
3. Group what remains into **pattern families**: patterns sharing the same base code whose signal-TIN sets overlap with Jaccard at least 0.6. For an `E1` pair, the family includes the single-code patterns of both codes if they meet the same overlap. The family's representative, and its dollar figure for ranking, is its highest-excess member that is **not** an `E1` pair, because pair excess includes dollars for a code that may have been billed anyway. If a family consists only of `E1` pairs (two codes that each existed before but have started appearing together), tag it `PAIR_ONLY`, rank it on half the pair excess, and let Stage 6 test T3 establish the incremental dollars.

This is the only place anything resembling clustering is used, and it is a deterministic merge.

### 8.4 Onset timing: staggered or synchronized

For each recurring pattern and each signal TIN carrying it, find the **onset month**: the first month, scanning forward from the start of the pre window, in which the TIN's monthly allowed on that pattern reaches half of its post-window monthly average. For `NEW_TO_TIN` patterns this is the first month billed.

```sql
-- BLOCK: B16_PATTERN_ONSET
CREATE OR REPLACE TABLE PIH_PATTERN_ONSET AS
WITH rec AS (
  SELECT TOKEN_TYPE, PATTERN_KEY FROM PIH_PATTERN_INDEX WHERE IS_RECURRING = 1 AND TOKEN_TYPE = 'P1'
),
carriers AS (
  SELECT sp.SUBJECT_ID, sp.PATTERN_KEY, s.VARIANT, s.PEER_GROUP_KEY, s.PROV_BIL_TIN,
         w.PRE_START, w.POST_START, w.POST_END, sp.A1P / w.K AS POST_MONTHLY
  FROM PIH_SUBJECT_PATTERN sp
  JOIN rec r ON r.TOKEN_TYPE = sp.TOKEN_TYPE AND r.PATTERN_KEY = sp.PATTERN_KEY
  JOIN PIH_SUBJECTS s ON s.SUBJECT_ID = sp.SUBJECT_ID AND s.ROLE = 'SIGNAL'
  JOIN PIH_WINDOWS w ON w.WINDOW_ID = sp.WINDOW_ID
  CROSS JOIN PIH_CONFIG c
  WHERE sp.IS_PRIMARY = 1 AND sp.EXCESS_ANNUAL >= c.MIN_PATTERN_EXCESS_USD AND w.PRE_START IS NOT NULL
),
monthly AS (
  SELECT c.SUBJECT_ID, c.PATTERN_KEY, l.SVC_MONTH, SUM(l.ALLOWED) AS A_M, MAX(c.POST_MONTHLY) AS POST_MONTHLY
  FROM carriers c
  JOIN PIH_LINES_S l
    ON l.VARIANT = c.VARIANT AND l.PEER_GROUP_KEY = c.PEER_GROUP_KEY AND l.PROV_BIL_TIN = c.PROV_BIL_TIN
   AND l.CODE = c.PATTERN_KEY AND l.SVC_MONTH BETWEEN c.PRE_START AND c.POST_END
  GROUP BY 1, 2, 3
),
onset AS (
  SELECT SUBJECT_ID, PATTERN_KEY, MIN(SVC_MONTH) AS ONSET_MONTH
  FROM monthly
  WHERE A_M >= 0.5 * POST_MONTHLY
  GROUP BY 1, 2
),
by_month AS (
  SELECT PATTERN_KEY, ONSET_MONTH, COUNT(*) AS N FROM onset GROUP BY 1, 2
)
SELECT
  PATTERN_KEY,
  SUM(N) AS N_CARRIERS,
  COUNT(*) AS N_DISTINCT_ONSET_MONTHS,
  MAX(N) * 1.0 / SUM(N) AS MODAL_ONSET_SHARE
FROM by_month
GROUP BY 1;
```

The block above handles `P1`. For other token types, change the join condition on `PIH_LINES_S` to match the token (for `P2`, `l.CODE || '|' || l.MODSET = c.PATTERN_KEY`, and so on).

Interpretation:

- **Synchronized** (`MODAL_ONSET_SHARE ≥ 0.60`, with at least 5 carriers): everyone started the same month. That points to an outside cause: a code-set change, a coverage or policy change, a fee schedule. Benign-leaning.
- **Staggered**: carriers started in different months. That points to a practice spreading from provider to provider, which is what a concept looks like.

### 8.5 Population view

For each recurring pattern, across **all** TINs in scope for the relevant cells (not just signals), compute monthly: dollars per active member-month, the number of TINs billing it (at least 10 lines in the month), and the share of dollars held by the top 10 TINs. Then tag:

| Tag | Rule | Reading |
|---|---|---|
| `SPREADING` | Number of billing TINs rose in at least 4 of the last 6 months, and onset is staggered | Strongest candidate |
| `ADOPTER_CLUSTER` | At most 20% of TINs that bill the base code carry the pattern, and those TINs' rate is at least twice everyone else's | Candidate: behavior of a subset |
| `UNIVERSAL_SHIFT` | At least 60% of TINs that bill the base code show an increase | Benign-leaning: something changed for everyone |

### 8.6 Pattern-level gates

| ID | Tag | Logic | Effect |
|---|---|---|---|
| PG1 | `NEW_CODE` | Pattern's code is "born" per gate S2. If the combined dollars per member-month of its `AHRQ_CAT` family are flat (within 10%) across the population, it is a relabeling | Relabeling: close. Otherwise keep, tagged |
| PG2 | `SYNCHRONIZED_START` | Section 8.4 | Second tier |
| PG3 | `UNIVERSAL_SHIFT` | Section 8.5 | Second tier |
| PG4 | `SINGLE_GROUP` | `IS_RECURRING = 0` but `SIGNAL_EXCESS_ANNUAL ≥ 100,000` | Not a concept. Write to a separate "provider leads" list |
| PG5 | `SINGLE_LOB_SYNC` | One LOB only, and synchronized | Second tier; likely a benefit or state policy change |
| PG6 | `NOT_ENRICHED` | `ENRICHMENT < 1.5` | Keep, tagged. The pattern may still be real, but the upstream signals are not what found it |
| PG7 | `EDIT_GAP` | If denial indicators exist: the pattern's denial rate is at least 50% on one `PLATFORM` and under 10% on another with at least $100,000 paid there | Promote to first tier regardless of other tags |
| PG8 | `KNOWN_CONCEPT` | Matches an entry in the list of existing payment integrity concepts, if one was supplied | Keep for the backtest; exclude from new dossiers |

### 8.7 Output of Stage 5

A ranked list of pattern families:

- **Tier 1:** recurring, and tagged `SPREADING`, `ADOPTER_CLUSTER`, or `EDIT_GAP`, with none of PG1 (relabeling), PG2, PG3, PG5.
- **Tier 2:** recurring, everything else not closed.
- Within a tier, sort by `SIGNAL_EXCESS_ANNUAL`, then `N_INDEP_GROUPS`.

Take the top 15 families of Tier 1 into Stage 6 (top up from Tier 2 if Tier 1 has fewer).

### 8.8 Stage 5 is done when

- The ranked list exists with all tags populated.
- The overall enrichment result is reported: of all recurring patterns, the share with `ENRICHMENT ≥ 2`, and the count of recurring patterns found among signals versus the count found if you swap roles (treat controls as signals and rerun 8.2).
- **Kill criterion.** If signals produce no more recurring patterns than controls, report that the upstream signals are not a useful seed for concepts, and recommend mining all series directly. Continue to Stage 6 anyway with what you have.

## 9. Stage 6: Hypothesis loop (agents)

One loop per pattern family. Four roles. Each role may only use the tables built above plus `SRC_CLAIM_LINES`. Cap each hypothesis at about 25 queries; if it is not resolved by then, record it as `INCONCLUSIVE` with what is missing.

### 9.1 Hypothesis agent

Input: the pattern family row, its tags, the list of carrying TIN groups (masked), the subject-level gate labels and flags, and Appendix A.

Output: a hypothesis card.

```yaml
hypothesis_id: H-0001
pattern_family: "<representative pattern key and its family members>"
mechanism: >
  One sentence: who bills what, under what condition, and why that would be an overpayment.
why_overpayment: >
  The principle that would make these lines non-payable or payable at a lower amount.
  Write "unknown: needs policy review" if you cannot name one. Do not invent citations.
rule_sql: >
  A WHERE clause (or small query) over claim lines that selects the affected lines.
rate_metric:
  numerator: "<affected lines, events, or units>"
  denominator: "<eligible lines, events, or member-months>"
prediction_if_true: "<what the tests below should show>"
prediction_if_benign: "<what they should show under the most likely benign explanation, named>"
flags_to_address: ["<every FLAG label on the carrying subjects>"]
```

A hypothesis without a `rule_sql` that runs is not a hypothesis. Send it back.

### 9.2 Test agent

Runs a fixed battery on the **full population** (all TINs, not just signals), and returns numbers only.

| Test | Query | Supports the hypothesis when |
|---|---|---|
| T1 Prevalence | Distribution of `rate_metric` across TINs with at least 30 denominator units: P50, P75, P90, P99. Where do the carriers sit? | Carriers sit far above P90; most TINs are near zero or near a common level |
| T2 Timing | `rate_metric` by month for each carrier | Staggered step-ups, each sustained |
| T3 Incremental dollars | Events with the pattern versus matched events without it (same anchor code and `DX3`, same peer group): difference in allowed per event | Events with the pattern cost more by about the pattern's own allowed amount (it is additive, not a substitute) |
| T4 Case mix | Compare the `DX3` distribution of carriers' patients on the affected services with non-carriers' | Similar diagnosis mix, so sicker patients do not explain it |
| T5 Platform and denial | `rate_metric`, denial rate, and allowed per unit by `PLATFORM` and `LOB_CAT` | Paid on one platform, denied or absent on another |
| T6 Persistence | If data after `DATA_END_MONTH` is available: does the rate hold? | It holds or grows |
| T7 Concentration | If `RENDERING_NPI` exists: share of affected lines by clinician within each carrier | Practice-wide (a billing policy) rather than one clinician (a provider lead) |
| T8 Member view | Share of a carrier's members who receive the pattern; repeat rate per member | High share regardless of diagnosis suggests routine application |

### 9.3 Red-team agent

Its job is to argue that the pattern is benign. For each explanation below it must run the stated check and return `REFUTED`, `SUPPORTED`, or `UNTESTABLE_WITH_CLAIMS`.

| Benign explanation | Check |
|---|---|
| Code-set change or relabeling | Family-level dollars per member-month flat while the code rose (PG1) |
| Fee schedule or contract | Pattern excess is price only; price ratio uniform across the carrier's items (gates P2, `PRICE_ONLY`) |
| Coverage or policy change | Synchronized onset; single LOB; appears across nearly all TINs |
| Sicker or different patients | T4 shows a shifted diagnosis mix that would justify the service |
| New service line or equipment | Pattern is `NEW_TO_TIN`, common among peers, at normal levels (gate S1) |
| Acquisition or consolidation | Carriers have V3 or V4 labels and the pattern came with the inherited patients at the same rate as at the donor |
| Data artifact | Any A-group flag on the carriers; the pattern is concentrated in a few members or one month |
| New drug, guideline, or technology | Staggered onset but adoption is heading toward universal, and carriers are simply early |
| Legitimate specialty difference | Carriers share a sub-specialty not captured by the peer group (check `PEER_GROUP_LEVEL`, taxonomy) |
| Already controlled | High denial rate on the pattern, or it matches a known concept (PG7, PG8) |

**Survival rule:** no explanation is `SUPPORTED`, and at most two are `UNTESTABLE_WITH_CLAIMS`. Untestable ones are carried into the dossier as "needs records or contract review."

### 9.4 Sizing

Size the concept across the whole population, not the signals.

- **Categorical rules** (the line should not be paid at all, such as an add-on without its primary): dollars are the allowed and paid amounts of every line matching `rule_sql` over the last 12 months of data.
- **Rate rules** (some level is normal, the excess is the issue): for each TIN with at least 30 denominator units, `excess units = max(0, TIN rate − benchmark) × TIN denominator`; `dollars = excess units × that TIN's average allowed per affected unit`. Report a range: benchmark at P90 (low estimate) and at P75 (high estimate).

Always report allowed and paid dollars, number of TIN groups, claims, and members, and the share of dollars in the top 10 TIN groups. A concept where one group holds most of the dollars is a provider lead.

### 9.5 Verdict and ledger

| Verdict | When |
|---|---|
| `SURVIVED` | Passes the survival rule; low-end sizing at least $250,000 allowed across at least `MIN_INDEP_GROUPS` groups |
| `PROVIDER_LEAD` | Real but concentrated in one or two groups |
| `BENIGN` | A benign explanation was `SUPPORTED`. Record which |
| `KNOWN` | Matches an existing concept |
| `INCONCLUSIVE` | Query budget exhausted or key data missing |

Every hypothesis is written to the ledger, including the ones that die. The ledger is what stops the next run from rediscovering the same benign pattern.

```sql
-- BLOCK: B17_LEDGER
CREATE OR REPLACE TABLE PIH_HYPOTHESIS_LEDGER (
  HYPOTHESIS_ID VARCHAR, RUN_DATE DATE, PATTERN_FAMILY VARCHAR, TOKEN_TYPES VARCHAR,
  MECHANISM VARCHAR, RULE_SQL VARCHAR, TIER VARCHAR, TAGS VARCHAR,
  N_INDEP_GROUPS INTEGER, ENRICHMENT DOUBLE,
  VERDICT VARCHAR, BENIGN_EXPLANATION VARCHAR, UNTESTABLE_ITEMS VARCHAR,
  SIZE_LOW_ALLOWED DOUBLE, SIZE_HIGH_ALLOWED DOUBLE, SIZE_LOW_PAID DOUBLE, SIZE_HIGH_PAID DOUBLE,
  N_TIN_GROUPS_AFFECTED INTEGER, TOP10_GROUP_SHARE DOUBLE,
  RECOMMENDED_ACTION VARCHAR, QUERIES_USED INTEGER, NOTES VARCHAR
);
```

On later runs, check each new pattern family against the ledger first. A family previously ruled `BENIGN` is skipped unless its dollars have at least doubled.

### 9.6 Dossier (survivors only)

One page, in this order:

1. **Mechanism** in one sentence, and the rule in plain words.
2. **Size:** low and high estimate, allowed and paid, TIN groups, claims, members.
3. **Evidence:** the T1 distribution, the T2 timing picture, the T3 incremental dollars.
4. **Benign explanations tested**, each with its verdict in a line.
5. **What claims cannot show**, and what record or contract review would settle it.
6. **Recommended action type:** pre-payment edit, post-payment review, policy clarification, provider education, or contract correction.
7. **The rule as SQL**, and the masked list of top TIN groups.

## Appendix A: Mechanism archetypes

Hints for naming a mechanism from a pattern's shape. They are prompts for the hypothesis agent, not policy statements.

| Pattern signature | Likely mechanism | Confirming test |
|---|---|---|
| `P2`: an office visit code with modifier 25 rising, plus an `E1` pair of that visit with a minor procedure | Modifier 25 applied routinely to bill a visit alongside a procedure | Share of procedure events that also carry a modified visit, versus peer P75 |
| `P2` with 59 or an X-series modifier on a code that forms an `E1` pair | Modifier used to bypass a bundling edit | Pair rate with versus without the modifier; denial rate of the unmodified pair |
| `P1` for an add-on code where the event lacks its usual primary | Add-on billed without primary | Find the codes that accompany the add-on in at least 95% of events population-wide; count events lacking all of them |
| `P5` shifting to higher units buckets, or piling up at one value | Units creep or billing to a limit | Units-per-line distribution versus peers; share of lines at the modal maximum |
| `W1` within-family mix rising with family volume flat | Upcoding within a code family | Level distribution versus peers, holding `DX3` mix fixed |
| `P3` shifting from office to facility site, or new facility-type lines for the same services | Conversion to facility billing | Same member, date, and code appearing on both professional and facility claims |
| `M1` shifting to higher frequency buckets | Frequency escalation (therapy, behavioral health, testing) | Service dates per member-month versus peers, by diagnosis |
| `E1` new pair appearing on most events regardless of diagnosis | Routine add-on testing or screening | Share of events with the pair, by `DX3`; flat across diagnoses suggests routine application |
| `N_CLAIM_IDS > 1` on netted lines, or the same service under two claim types | Duplicate billing | Count of netted lines with more than one claim ID, by carrier |
| `P4` showing a code newly paired with a specific diagnosis | Diagnosis chosen to meet coverage | First appearance of that diagnosis in the member's history coincides with the service |
| `P5` or `P2` on drug codes: units jump, or wastage modifiers appear | Drug units or wastage billing | Units per administration versus peers; share of lines with wastage modifiers |
| `P1` for new-patient visit codes among `CONTINUING` members | New-patient codes billed for established patients | Members with a prior visit at the TIN who are billed a new-patient code |
| `E1` with many lab codes per event | Panel components billed separately | Count of distinct lab codes per event versus peers |
| `P3` with telehealth sites or modifiers at full facility rates | Telehealth billed at in-person or facility rates | Allowed per unit by site for the same code |
| `M1` or `P5` on time-based codes with implausible totals | Impossible day (needs rendering NPI) | Sum of timed units per clinician per day |
| `NONPAR` variant, price-only pattern, allowed tracks billed | Charge inflation out of network | Gate P5 at the pattern level |
| `BILLED_CODE` differs from `CODE` at a rising rate | Payment on a remapped code | Share of lines where they differ, and allowed per unit for each mapping |

## Appendix C: What was verified, and what was not

**Verified.** Every SQL block with a `-- BLOCK:` header (26 blocks) was extracted from this file and executed in order on synthetic claims, in DuckDB with small shims for two Snowflake functions (`DATEADD`, `ARRAY_CONSTRUCT_COMPACT`). The synthetic data had 40 TINs in one peer group over 30 months, with reversed-and-rebilled lines mixed in. Five TINs were set up as signals:

| Synthetic signal | What was injected | What the pipeline did |
|---|---|---|
| Two standard-history TINs | 30% more patients, a new add-on procedure billed on half of visits with modifier 25 on the visit code, and a 5% price rise | Passed. Intensity of about $29K and $31K a year against an injected add-on worth about $32K; patient growth landed in volume (about $42K and $35K) and the price rise in price (about $5K to $6K each) |
| One limited-history TIN | The same add-on billing from its first month | Passed on the level track, with lines per event at 1.46 times the peer median |
| One pure-growth TIN | 40% more patients and nothing else | Closed as benign, reason `VOLUME`; intensity about $500 |
| One spike TIN | A single month at three times normal volume | Closed as an artifact by gate A7 |

Other checks:

- The decomposition identity held to within a billionth of a dollar for every TIN and window.
- Matched controls showed intensity of about $1K and produced no candidate patterns.
- The pattern index listed the add-on code, the modified visit codes, and the code pair, each carried by all three TINs that had the injected billing and by no control.
- The sum of `P1` pattern excess was within about 12% of `TOTAL_ADJ − VOLUME_ADJ` for the altered TINs.
- Netting removed the reversal pairs and left total allowed unchanged.
- The test confirmed the two interactions described in Section 5.1: added cheap lines raised `LINES` and lowered `MIX`, and patient growth raised `PANEL` and lowered `FREQ`.

Testing changed the design in three places: `FREQ` was moved from intensity to volume, gate A7 gained the requirement that a step exists, and `BENIGN_REASON` was restricted to closed-benign subjects.

For the test only, three thresholds were lowered because the synthetic practices are small (`MIN_INTENSITY_USD` 20,000; `MIN_INDEP_GROUPS` 2; `MAX_TOP_GROUP_SHARE` 0.70), and `PIH_TIN_GROUP` was stubbed with each TIN as its own group.

**Not verified.**

- Nothing has run on Snowflake or on real claims. Expect small dialect fixes.
- Column names for modifiers, rendering NPI, denial indicators, and geography are placeholders.
- Blocks marked `-- SKETCH` were not executed.
- Gates described only in the catalog (most of groups A, V, P, S, R) are specified but not coded here; implement them from the catalog following the pattern in block G07.
- Section 7.4 (within-family mix) is specified as math, not code.
- All thresholds are reasoned defaults. None has been tuned on data.
